## Информационная база и запуск

Работа с приложениями, информационными базами, расширениями, тестами и живыми данными.

> [!CAUTION]
> Инструменты этой группы могут запускать 1С, изменять ИБ или перезаписывать конфигурацию. Перед операциями **Опасно** сделайте резервную копию.

| Инструмент | Режим | Назначение |
|---|---|---|
| `get_applications` | Чтение | Показывает приложения и информационные базы проекта. |
| `list_registered_infobases` | Чтение | Весь список баз EDT, не только проекта: `groups` и `infobases[]` с группой (путем), типом, строкой соединения, дополнительными параметрами с замаскированными паролями и версией платформы, плюс привязанные проекты (`projectsNotRead` - проект, чью привязку прочитать не удалось). |
| `list_configurations` | Чтение | Возвращает клиентские и Attach-конфигурации запуска EDT. |
| `update_database` | Опасно | Обновляет конфигурацию информационной базы. С `statusOnly=true` читает отслеживаемые обновления вместо запуска: `updates[]` с `runKey`, состоянием и прогрессом, отбор по `projectName`; ничего не запускает и не забирает готовый результат, ключ чужого вида работы отвергается. Перед чтением состояния обновляет проект и родителя расширения с диска (`refreshWorkspace`, по умолчанию true): файлы, записанные мимо сервера (файловый инструмент, git checkout, pull), модели иначе невидимы, и ответ несет `workspaceRefresh.changedResources`. С `protectData=true` (по умолчанию) обновление, которое удалило бы данные, не начинается: `confirmationRequired` с `dataLossTables` и `dataLossCount`; `acceptDataLoss=true` - решение пользователя. Инкрементальное обновление отказывает (`infobaseChanged`), пока хранимая копия `ConfigDumpInfo.xml` описывает другую базу или базу, замененную загрузкой `restore_database_snapshot`; `verifyInfobaseContent=true` сверяет копию с самой базой перед обновлением. |
| `inspect_database_sync` | Чтение | Отвечает сравнением защиты данных без запуска обновления: блок `dataLossProtection` (`pendingDataLoss`, `pendingDataLossCount`, `baseline`, `dataLossCheck`, `nextStep`, `dataLossCompared`, `acceptDataLossDefault`), `nothingStarted: true`; настройка `restructureConfirmationPrompt` базы читается, не пишется. |
| `export_database_snapshot` | Опасно | Выгружает всю базу в один `.dt` (`path`; существующий файл - `alreadyExists`): дамп пишет запуск толстого клиента во временный файл и переносится, только когда непуст и создан этим прогоном (`outputMissing`). Монополия на базу, `timeoutSeconds` 5-120 (по умолчанию 30), дольше - `Pending` с `runKey`. |
| `restore_database_snapshot` | Опасно | Загружает `.dt` в базу: сперва пишет резервную копию текущего содержимого (`backupTo`, без него - `<имя>-backup-<время>.dt` рядом с файлом; занятый путь - `alreadyExists`, отсутствующий или пустой исходный файл - `inputMissing`), без копии не начинается и заменяет все, что база держит. Отказ после записанной копии тоже называет `backup`. Успешная загрузка помечает хранимую копию `ConfigDumpInfo.xml` (`copyMarked`), и инкрементальное `update_database` отказывает до `sync_control operation=rebuild_dump_info`. |
| `retrieve_database_changes` | Опасно | Подтягивает изменения базы в проект (направление, обратное `update_database`): проект с собственными правками отказывается до `replaceLocal=true`, толстый клиент, запущенный EDT, - по имени запуска (`heldBy`). `timeoutSeconds` 30-3600 (по умолчанию 300), дольше - `Pending` с `runKey`. |
| `debug_launch` | Выполнение | Запускает клиент или подключается к серверу отладки 1С. `startupOption` - строка `/C` для клиента (autostart, /Execute, адрес отладчика), пишется в копию конфигурации запуска, сохраненная не меняется; Attach-конфигурация и уже запущенный без них сеанс ее отвергают. `waitForEndpoint` с `endpointTimeoutSeconds` (1..50, по умолчанию 20) превращают ответ в отчет готовности: GET на адрес, готово когда итоговый статус ниже 500, не больше пяти перенаправлений, одно чтение не дольше 5 секунд; неответивший адрес - отказ, клиент НЕ останавливается. Те же доводы у `start_client` фасада `infobase_admin`. Attach-конфигурация отвергает и `startupOption`, и `waitForEndpoint` - она не стартует клиента и не открывает адрес. `clientType` (`thin`, `thick`, `web`) и `runMode` (`ordinary`, `managed`): конфигурация обычного приложения стартует в толстом клиенте, флаг режима кладется на ссылку базы в сеансе, ответ несет `clientType`/`runMode` с источниками и `runModeFlagState`. |
| `run_yaxunit_tests` | Выполнение | Запускает YAxUnit и читает JUnit-отчет. |
| `yaxunit_tests` | Фасад · Выполнение | Единая точка запуска и отладки тестов YAxUnit. |
| `vanessa` | Выполнение | Запускает сценарии Vanessa Automation и снимает форму в работающей 1С. Сценарий берется файлом (`featurePath`), текстом (`scenarioText`) или собирается из `formToOpen` - тогда шаг открытия задается `openStep`, у формы списка, формы объекта и формы расширения он свой. Шагу открытия нужны типы интерфейсного тестирования: они есть только в клиенте, запущенном менеджером тестирования (`testManager`), иначе шаг отвечает `Тип не определен (ТестируемаяГруппаФормы)`. Клиент для шага запуска называется `testClient`, порт - `testClientPort`, пользователь базы - `infobaseUser` (пароль отвергается). Результат читается из файлов `<uuid>-result.json`, которые Vanessa называет сама. Доводы списка собирают действие целиком: `listKind` с `listName` открывают список, `tableName` называет таблицу формы (по умолчанию `Список`), `column` с `columnValue` переходят к строке (`whenSeveral`), `buttonTitle` или `buttonName` нажимает кнопку, `windowTitle` и `windowWaitSeconds` задают ожидание окна. На ветках списка и `formToOpen` кадр сохраняет шаг «И я сохраняю скриншот» в `frame-after-action.png` каталога снимков: VanessaExt рисует в файл верхнее окно клиента тестирования, что бы его ни перекрывало; `testManager` и `testClient` там включаются сами, клиент открывает базу проекта, пользователь входит ключом `/N`. На ветках `featurePath` и `scenarioText` способ снимка берется из настроек самой Vanessa. |
| `create_launch_config` | Изменение | Создает конфигурацию запуска EDT, привязывая базу в текущем контексте привязки проекта (в ветке у проекта под версионным контролем); клиент - по режиму запуска конфигурации. |
| `create_infobase` | Опасно | Создает информационную базу и связывает ее с проектом. |
| `register_infobase` | Изменение | Регистрирует СУЩЕСТВУЮЩУЮ базу - файловую (`path`) или серверную (`connectionString`) - в списке EDT и связывает с проектом одним вызовом, с учетными данными базы (`accessMode`, `userName`, `password`). |
| `delete_infobase` | Опасно | Удаляет информационную базу. |
| `install_extension` | Опасно | Устанавливает расширение в информационную базу. |
| `uninstall_extension` | Опасно | Удаляет расширение из информационной базы. |
| `list_extension` | Чтение | Показывает установленные расширения. |
| `import_configuration_from_xml` | Опасно | Импортирует XML конфигурации с возможной перезаписью проекта. |
| `export_configuration_to_xml` | Изменение | Экспортирует конфигурацию в XML. |
| `export_extension` | Изменение | Экспортирует расширение конфигурации. |
| `set_infobase_credentials` | Опасно | Изменяет сохраненные учетные данные подключения к ИБ. |
| `sync_control` | Опасно | Управляет направлением и состоянием синхронизации проект ↔ ИБ. |
| `resync_to_disk` | Опасно | Принудительно синхронизирует модель EDT на диск. |
| `restart_edt` | Опасно | Перезапускает выбранный экземпляр EDT. |
| `delete_project` | Опасно | Удаляет проект из рабочего пространства. |
| `self_upkeep` | Чтение | Сообщает, опубликована ли на update site сборка плагина новее установленной. |
| `infobase_admin` | Фасад · Смешанный | Объединяет жизненный цикл ИБ и обновление конфигурации. |

> Данных информационной базы плагин не отдает: `browse_data`, `execute_query` и фасад `data_access` из него
> удалены. Запрос к живой базе - только через скил `1c-mcp-toolkit`.
>
> Исключение - журнал регистрации ФАЙЛОВОЙ базы: он лежит файлами рядом с ней и читается
> `infobase_admin operation=read_event_log` без платформы и без запущенной базы. Таблицы базы
> по-прежнему недоступны, серверная база и формат `1Cv8.lgd` отвечают именованным отказом.

Квитанции прогонов (0.2.56): завершенный прогон `vanessa` тоже пишет `receiptPath` (те же
`run-receipts`, не больше 20 последних); ответ называет файлы, которые написала сама Vanessa (`resultsDir`,
`resultFiles`), и `junitXmlPath`, когда результат прочитан из JUnit-отчета. Прогон, упершийся в таймаут,
перед остановкой процесса читает окна клиента 1С, которые его держат, и отвечает `blockingWindows`
(`pid`, `title`, `texts`, `buttons`, `modal`, `imageFile` при сделанном снимке; пустой список, когда окон
не нашли) и `blockingWindowsError` (только когда окна прочитать не удалось); строка окна
длиннее 500 символов обрезается, выводится не больше 20 строк одного вида, остаток назван числом. Снимки
`blocking-*.png` лежат рядом с квитанциями под тем же пределом числа файлов.

## Отладка и профилирование

Полный цикл управления приостановленной BSL-сессией.

| Инструмент | Режим | Назначение |
|---|---|---|
| `set_breakpoint` | Выполнение | Устанавливает строковую точку останова BSL. `replaceModuleSet` очищает адресованные модули от точек до постановки пачки - пачка становится их полным набором (`removedCount`, `clearedModules`). |
| `set_breakpoint_state` | Выполнение | Включает или выключает точку останова, не снимая ее: строка, условие и счетчик попаданий сохраняются (`breakpointEnabled` обязателен, ответ несет `changed`). |
| `remove_breakpoint` | Выполнение | Удаляет точку останова. |
| `list_breakpoints` | Чтение | Показывает активные точки останова. |
| `wait_for_break` | Выполнение | Ожидает приостановку и возвращает поток, стек и кадры. |
| `pause_thread` | Выполнение | Просит сессию приостановиться: `threadId` называет один поток, без него - все потоки. `outcome`: `paused` (поток, стек, `topFrameRef`), `request_armed` (приостановки за `timeoutSeconds` не случилось), `terminated`, `error`. |
| `get_variables` | Чтение | Читает переменные выбранного кадра стека. |
| `step` | Выполнение | Выполняет step over, step into или step out. |
| `resume` | Выполнение | Продолжает выполнение приостановленного потока. |
| `evaluate_expression` | Выполнение | Вычисляет BSL-выражение в контексте кадра. |
| `debug_yaxunit_tests` | Выполнение | Запускает тесты YAxUnit в режиме отладки. |
| `debug_status` | Чтение | Возвращает активные debug targets, потоки и состояние suspend. |
| `start_profiling` | Выполнение | Включает или выключает замер производительности. |
| `get_profiling_results` | Чтение | Возвращает измерения по модулям и строкам. |
| `launch_debugger` | Фасад · Выполнение | Объединяет запуск, breakpoints, stepping, variables и profiling. |
| `run_to_line` | Выполнение | Продолжает выполнение до выбранной строки. |
| `set_exception_breakpoint` | Выполнение | Настраивает остановку по исключениям. `catchAll` без `message` по умолчанию true; `catchAll=false` без `message` отвергается до создания точки - точка с пустым условием не ставится. |
| `set_variable` | Выполнение | Изменяет значение переменной приостановленного кадра. |
| `terminate_launch` | Выполнение | Завершает выбранный debug launch. |

**Открытый редактор виднее файла.** `read_module_source` отдает несохраненные правки редактора и помечает это в ответе; `write_module_source` при таком редакторе отказывает. То есть прочитанное и записанное относятся к одному состоянию, а не к разным.

Ссылка на кадр не переразрешается после новой остановки (0.2.56): `get_variables` несет адрес кадра в
ответе, индекс вне стека отвергается, нечитаемая область названа в `scopeFailures`; значение из
`set_variable` в журнал не попадает; длинный результат `evaluate` обрезается с `truncated` и `fullLength`,
а при исчерпании ожидания ответ говорит, что выражение еще считается. Запуск с обновлением базы
отказывает, если база не пришла в `UPDATED` (обновление уже идет, загрузка закончилась другим состоянием,
приложение не нашлось или не разрешилось): отказ несет `databaseUpdate` и `databaseState`, запущенная
сессия - `databaseUpdate`; `FULL_UPDATE_REQUIRED` ведет к полному обновлению, проверка "уже запущено"
идет до обновления.
