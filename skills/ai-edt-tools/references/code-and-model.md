## Исследование модели

Семантическая модель EDT, документация платформы, объекты метаданных и связи между ними.

| Инструмент | Режим | Назначение |
|---|---|---|
| `get_content_assist` | Чтение | Возвращает подсказки EDT и сведения о типах в позиции BSL. Пакет позиций одним вызовом: `positions` - массив объектов со своими `filePath` (по умолчанию верхнеуровневый), `line`, `column`; сбойная позиция отвечает своей ошибкой и не останавливает остальные. Чтение символа из файла модуля берет кодировку самого файла, не только UTF-8 (0.2.57). |
| `get_platform_documentation` | Чтение | Ищет методы, свойства и конструкторы типов платформы 1С. Имя разрешается через реестр наборов типов: набор (`СправочникСсылка` и подобные) отвечает перечнем охватываемых типов, отдельный член набора - отказ с причиной; без `projectName` читается новейшая платформа рабочего пространства и ответ называет версию; `limit` не больше нуля - отказ. |
| `get_metadata_objects` | Чтение | Получает список объектов метаданных с фильтрами. Язык синонима разрешается по коду, ячейки Markdown экранируются; для внешнего проекта фильтр типа не заявляется (0.2.58). |
| `get_metadata_details` | Чтение | Возвращает реквизиты, табличные части, формы и другие свойства объектов. |
| `find_references` | Чтение | Ищет семантические ссылки на объект в метаданных, формах, ролях и BSL. ### `ai_context` - размер ответа и число методов

Замер пяти общих модулей: ответы `ai_context` с `depth=standard` по умолчанию занимали
5173-5945 символов, ответы `read_module_source` - 64706-225721 символов, до 5000 строк исходника
за вызов. `standard` по умолчанию перечисляет не больше 30 методов модуля (`maxMethods`).

### `find_dead_code` - отбор неиспользуемых экспортных методов

Сначала строковые вызовы собираются из всех модулей и форм, вне фильтров кандидатов; затем
выбираются кандидаты. Предел попыток загрузки кандидатов - 5000, внешних модулей - 20000,
независимо друг от друга; неудачные загрузки также учитываются. Частичный ответ не подтверждает
отсутствие неиспользуемого кода.

## Исходный код BSL

Чтение, изменение и семантическая навигация по модулям.

| Инструмент | Режим | Назначение |
|---|---|---|
| `read_module_source` | Чтение | Читает BSL-модуль целиком или по диапазону строк. |
| `write_module_source` | Изменение | Записывает модуль. Режимы шире, чем replace / append / searchReplace: есть `replaceMethod` (заменяет метод вместе с его ведущей шапкой), `replaceLines` (с проверкой `expectedText`), `insertBefore` / `insertAfter`, `replaceMethods` (несколько методов атомарно). В режимах append, insertBefore и insertAfter вставленный целый метод отделяется пустой строкой от соседнего кода (0.2.57). **Перед первой записью в модуль прочитать `rules/edt-bsl-write-safety.md`: голый `replace` перезаписывает модуль целиком и затирает чужой код.** `normalizeInvalidCharacters` (по умолчанию true) заменяет тире U+2012-U+2015 и U+2212 дефисом, U+00A0 - пробелом, U+00AD убирает, вне строковых литералов BSL; ответ несет `invalidCharactersReplaced` и `invalidCharactersPositions` (строка и колонка, первые 50 - с пометкой, когда список обрезан). |
| `get_module_structure` | Чтение | Возвращает методы, области, параметры и контексты выполнения. Границы области - от пары `#Область` / `#КонецОбласти` в тексте и модели: конец на строке закрывающей директивы, незакрытая область - до последней строки модуля; `Params` читает подпись, разбитую на строки, сохраняя скобки умолчаний. |
| `list_modules` | Чтение | Показывает BSL-модули проекта с фильтрами. |
| `search_in_code` | Чтение | Выполняет текстовый или regex-поиск по BSL. |
| `read_method_source` | Чтение | Читает конкретную процедуру или функцию. |
| `get_method_call_hierarchy` | Чтение | Ищет вызывающие или вызываемые методы. |
| `go_to_definition` | Чтение | Разрешает символ и возвращает место определения. |
| `get_symbol_info` | Чтение | Возвращает hover/type information в позиции BSL. |
| `validate_query` | Чтение | Проверяет синтаксис и семантику запроса 1С. |
| `code_search` | Фасад · Чтение | Объединяет поиск, ссылки, определения, hierarchy и content assist. |

### `write_module_source` - путь нового модуля и неизмененный файл

Канонический файловый layout проверяется при создании НОВОГО файлового модуля, в том числе при
`dryRun=true`. Существующий файл пропускает последующие проверки layout; адрес модуля, который
предоставляет другой бандл, не является файловым layout.

Первый сегмент - имя каталога вида (`CommonModules`, не `CommonModule`); отказ называет полный
канонический путь. Все каталоги пути должны существовать: файл модуля может быть новым, в том числе
`ManagerModule.bsl`, но объект, форма, команда или вложенный объект конфигурации должны существовать.
Имя файла проверяется по месту, которого достиг путь, а не только по верхнему виду:

| Место | Допустимые имена модулей |
|---|---|
| Общий модуль | `Module.bsl` |
| Справочник | `ObjectModule.bsl`, `ManagerModule.bsl` |
| Регистр | `RecordSetModule.bsl`, модуль менеджера |
| Константа | `ValueManagerModule.bsl` |
| Форма | `Module.bsl` |
| Команда | `CommandModule.bsl` |
| Таблица внешнего источника данных | Модули объекта, набора записей и менеджера |
| Таблица измерения куба | Модули объекта и менеджера |
| Перерасчет регистра расчета | Только `RecordSetModule.bsl` |

Отказ перечисляет допустимые имена модулей или уровни вложенности, если путь содержит чужой уровень
либо вид без собственного модуля. Модули корня конфигурации сохраняют адреса вида
`Configuration/SessionModule.bsl`. Чтение не меняет поведения: для отсутствующего файла с первым
сегментом-именем вида вместо каталога отказ называет канонический путь.

`unchanged:true` возвращается только при точном совпадении байтов синхронизированного файла:
перезаписи и принудительного экспорта нет. Файл в состоянии out-of-sync таким ответом не считается.
