## Обозначения

| Метка | Значение |
|---|---|
| **Чтение** | Не должен изменять проект или информационную базу. |
| **Изменение** | Записывает исходники, метаданные, настройки или файлы проекта. |
| **Выполнение** | Запускает EDT/1С, тесты, запросы или код в живой сессии. |
| **Опасно** | Может удалить, импортировать, перезаписать или синхронизировать данные. |
| **Смешанный** | Поведение зависит от выбранной операции или параметров вызова. |
| **Фасад** | Единая точка входа для нескольких родственных операций. |
| **Workshop** | Высокоуровневый конструктор сложного артефакта. |

## Ключевые фасады

Фасады уменьшают размер `tools/list`: вместо набора родственных standalone-инструментов агент видит одну точку входа и выбирает действие через параметр `operation`.

У большинства фасадов встроена справка:

```json
{
  "operation": "help"
}
```

Для подробностей конкретной операции используется `topic`:

```json
{
  "operation": "help",
  "topic": "text_search"
}
```

### `code_search` - поиск и навигация по коду

Операции: `text_search`, `object_references`, `method_references`, `resolve_symbol`, `call_hierarchy`, `symbol_info`, `content_assist`, `outgoing_structures`, `help`.

Используйте фасад для исследования BSL и модели перед изменениями. 
Все операции только читают проект.

У `call_hierarchy` есть `depth`: он уходит дальше непосредственных соседей, до пяти уровней, циклы отбрасываются, а не обходятся по кругу.

У `text_search` `projectName` НЕОБЯЗАТЕЛЕН: без него ищутся все открытые проекты с исходниками, а ответ называет их поименно. Это важно, когда рядом лежат конфигурация и ее расширения - пустой ответ по одному проекту читается как "такого текста нет вообще". Явно названный несуществующий проект остается ошибкой.

### `launch_debugger` - полный цикл отладки

Объединяет запуск/Attach, line и exception breakpoints, `run_to_line`, ожидание suspend, чтение и изменение переменных, stepping, resume, terminate, evaluation и profiling.

Большинство операций требует действующей конфигурации запуска EDT; операции с кадрами требуют приостановленного потока.

`action=launch` открывает в запускаемом клиенте внешнюю обработку или отчет: `externalObjectName` называет объект, `externalObjectProject` - проект внешних объектов, когда это не тот проект, который запускается. Имя, которое не разрешается, останавливает запуск ДО обновления базы, и ответ несет `nothingWasLaunchedOrUpdated`. Произвольного пути к `.epf` у запуска нет - объект разрешается только из проекта внешних объектов, поэтому готовый бинарник сперва заводится в проект через `external_object_workshop operation=import_external_object`, и это ЕДИНСТВЕННЫЙ маршрут.

Среда открывает такой объект, СОБИРАЯ его, поэтому у проекта внешних объектов должна быть включена
генерация дампа. На свежесозданном проекте она выключена, и клиент тогда стартует с пустым экраном.
Запуск отказывает и называет проект; `enableExternalObjectDump=true` включает генерацию для этого
проекта и продолжает запуск.

`debugServerPort` дает запуску свой порт отладочного сервера (1..65535). На машине один порт по
умолчанию на все запущенные среды, и второй начавший отладку получает окно «порт уже используется» -
это способ разойтись. Сохраненная конфигурация запуска не меняется.

Клиент следует режиму запуска конфигурации (0.2.53). Конфигурация с основным режимом обычного
приложения стартует в толстом клиенте: конфигурация запуска, которую создает запуск, сохраняется с
толстым клиентом, существующая запускает этот запуск с ним, а `/RunModeOrdinaryApplication` кладется
в дополнительные параметры запуска базы на ссылке, которую EDT держит в сеансе, - список баз на
диске не пишется; управляемый запуск убирает флаг. `clientType` (`thin`, `thick`, `web`) и `runMode`
(`ordinary`, `managed`) называют выбор прямо; `clientType=thin` у такой конфигурации без
`runMode=managed` отвергается. Ответ несет `clientType`, `clientTypeSource`, `runMode`, `runModeSource`,
`runModeFlagState` (`added`, `removed`, `present`, `absent`, `not applied: ...`), `runModeFlagScope`,
`infobaseAdditionalParameters`; решение принимается до обновления базы.

Успех ставится только по НАБЛЮДАЕМОЙ живой цели отладки. Отказ называет увиденное - запуск не
создан, завершился сразу, все цели завершены, цель не появилась за десять секунд - и перечисляет
модальные окна, открывшиеся во время запуска.

`action=wait_for_break` ждет **не больше 50 секунд** и 50 по умолчанию, под всеми четырьмя именами
довода (`timeoutSeconds`, `timeoutMs`, `waitSeconds`, `timeout`): один запрос дольше не живет, и
просьба на 300 секунд раньше возвращалась ошибкой транспорта вместо ответа. Урезанное ожидание несет
`timeoutCapped` и `waitedSeconds`; точки останова остаются расставленными, так что ждать дальше -
это следующий вызов.

`action=get_variables` помечает записи, для которых API переменных не отдал значения, полем
`valueNotReturnedByVariables` и считает их: значения читаются по одному - `expandPath=<имя>` (он при
промахе вычисляет имя) или `action=evaluate`. Переменная с пустой строкой не помечается: пустое
значение - это ответ.

Когда приложение не разрешается само, отказ перечисляет все увиденные запуски с конфигурацией,
типом, идентификатором приложения и числом целей отладки.

### `diagnostics` - диагностика и валидация

Операции: `get_project_errors`, `get_problem_summary`, `revalidate_objects`, `clean_project`, `validate_for_export`, `get_check_description`, `help`.

`marker_corrections` стоит рядом с ними отдельным инструментом: он применяет к найденной проблеме то
штатное исправление, которое предлагает сама проверка. Работает в два шага - сначала список доступных
исправлений для находки, затем применение выбранного по его описанию из списка. Нужны `projectName` и
`checkId`. Это не "починить все": исправление есть не у каждой проверки.


### `project_admin` - проекты и рабочее пространство


`list_subsystems` стоит отдельного упоминания: он отдает подсистемы иерархией вместе с составом
(FQN входящих объектов) и признаком, есть ли на диске `CommandInterface.cmi`. Плоский список имен от
`get_metadata_objects` этого не показывает. Наличие или отсутствие `.cmi` инструмент подает как факт,
а не как ошибку - трактовку смотреть в правиле `edt-zip-export-pitfalls.md`.
Три операции требуют оговорки:

- **`resync_to_disk`** сбрасывает модель объектов из памяти EDT на диск. Звать ПЕРЕД
  `update_database` и перед экспортом конфигурации: именно рассинхрон памяти и диска дает класс
  ошибок "валидно в EDT, падает в ИБ" и `zip:///` not-found. Ссылки в `Configuration.mdo` он при
  этом не чистит - это другой дефект. Подробности в правиле `edt-zip-export-pitfalls.md`.
- **`delete_project`** разрушительна. По умолчанию (`deleteContent=false`) проект только
  отключается от рабочей области, файлы остаются на диске и импортируются обратно;
  `deleteContent=true` стирает и файлы.
- **`restart_edt`** перезапускает или гасит саму EDT, внутри которой работает плагин. После нее
  сервер отвечает не сразу.
- **`answer_dialog`** нажимает названную кнопку модального окна, на котором стоит EDT: такое
  окно держит workbench, и снаружи это неотличимо от зависания. Читать окно - `self_status`
  либо поля `blockedByDialog` и `dialogs` в ответе долгой операции со `status=Pending`;
  нажимать - назвав кнопку в `button`. Само по себе не нажимается ничего, а имя, не совпавшее
  ни с одной кнопкой или совпавшее с несколькими, отвергается.


Операции: `list_projects`, `list_configurations`, `get_configuration_properties`, `create_project`, `delete_project`, `resync_to_disk`, `restart_edt`, `answer_dialog`, `list_subsystems`, `help`.

Часть операций изменяет рабочее пространство или перезапускает EDT.

**История вызовов.** `get_mcp_history` отдает список последних вызовов, урезанный до нескольких сотен
знаков на запись: буфер живет в куче самой среды. Полный текст лежит рядом на диске - довод `entryId`
из записи списка отдает ОДИН вызов целиком, с полными доводами и полным ответом, замаскированными так
же, как в журнале. Запись, которой в кладовой больше нет, получает названный отказ, а не урезанную
копию под видом полной; `entryId` вместе с `clear` отвергается. Что хранится на диске, задается на
странице настроек в группе «Call history on disk»: хранить ли полный текст, сколько дней хранить (14
по умолчанию, ноль - до предела размера) и в какой папке. При выключенной записи вызовов на диск не
пишется ничего.

### `infobase_admin` - жизненный цикл информационной базы

Объединяет `get_applications`, `list_registered_infobases`, `read_event_log`, `create_infobase`, `delete_infobase`, `set_infobase_credentials`, `create_launch_config`, `start_client`, `update_database`, `branch_infobase`, `inspect_database_sync`, `export_database_snapshot`, `restore_database_snapshot`, `sync_control` и встроенную справку. С `dryRun=true` ничего не запускается: ответ несет состояние обновления (`updateState`), признак `wouldUpdate`, готовность базы (`readiness`) и ее проблемы (`readinessProblems`). Прогон не записывается, база не занимается. Состав изменений по объектам так недостижим, и ответ говорит это в `composition`.

`branch_infobase` связывает ветку git с приложением проекта, после чего `update_database` отказывается обновлять базу, привязанную к другой ветке. У проекта-РАСШИРЕНИЯ привязка лежит в самом расширении, а не в конфигурации, которую оно расширяет.

`start_client` принимает те же `clientType` и `runMode`, что и `launch_debugger action=launch`
(0.2.53): конфигурация обычного приложения стартует в толстом клиенте, ответ говорит, что решено и что
изменено. `create_launch_config` привязывает базу к проекту в текущем контексте привязки - в ветке у
проекта под версионным контролем. `sync_control` читает хранилище сигнатур там, где его ведет EDT
2026 - в рабочей области, в служебной папке проекта, затем в `%APPDATA%/.1cedt/ib-sync/ss` старых
EDT (у каждой базы в `status` указан `store`), и читает и переписывает `index.idx` версионного
формата EDT 2026.

`read_event_log` (с 0.2.27) читает журнал регистрации ФАЙЛОВОЙ базы - кто входил, что проводилось, что платформа отвергла, - с отбором по `from` / `to` / `event` / `user` / `severity`. Серверная база и однофайловый SQLite-формат `1Cv8.lgd` отвечают именованным отказом, а не пустым списком.

**`start_client`** запускает клиент 1С:Предприятие из конфигурации запуска EDT, без отладчика.
Плагин прямо просит звать его ВМЕСТО сборки командной строки `1cv8.exe` руками: версия runtime,
база, вид клиента и пользователь берутся из настроек среды, а не собираются агентом по памяти.

**`create_launch_config`** привязывает СУЩЕСТВУЮЩУЮ базу к проекту - создать ее заранее должен
`create_infobase`. Привязка идет как несинхронизированная, поэтому сразу после нее
`get_applications` честно сообщит, что базу нужно обновить.

**`delete_infobase`** по умолчанию убирает базу только из списка EDT; `deleteContent=true`
удаляет и каталог `.1CD` с диска - необратимо. **`set_infobase_credentials`** хранит пароль
зашифрованным, в ответ отдает лишь признак `passwordStored`, в журнал пароль не попадает.


`update_database` по проекту-РАСШИРЕНИЮ обновляет базу той конфигурации, которую расширение расширяет, и `applicationId` для этого не нужен: без него берется приложение по умолчанию - свое, затем родительское. Отказ называет тех держателей базы, кого сервер видит (клиенты, запущенные EDT, и соседние экземпляры AI-EDT), и честно говорит, кого он видеть не может.

`register_infobase` (0.2.55) заводит СУЩЕСТВУЮЩУЮ базу в список EDT и связывает ее с проектом одним
вызовом: файловую по `path`, серверную по `connectionString` (`Srvr=...;Ref=...`), ровно одно из двух.
`accessMode` / `userName` / `password` пишут учетные данные базы в том же вызове, до привязки: база с
пользователями регистрируется без окна запроса доступа, пароль не попадает ни в ответ, ни в историю.
Адрес-дубль используется повторно (`reused`), имя, занятое базой с другим адресом, отклоняется
(`alreadyExists`), сбой привязки снимает добавленную запись. `makeDefault` по умолчанию true только у
проекта без приложения по умолчанию; ответ называет прежнее и новое (`previousDefaultApplication`,
`defaultApplication`).

`list_registered_infobases` (0.2.56) отдает весь список баз EDT, а не только проекта: `groups` и
`infobases[]` с группой (путем), типом, строкой соединения, дополнительными параметрами с замаскированными
паролями и версией платформы, плюс привязанные проекты; проект, чью привязку прочитать не удалось, назван в
`projectsNotRead`.

Запись списка баз (`register_infobase`, `set_infobase_credentials`, `create_infobase`,
`delete_infobase`) не отвязывает конфигурации запуска от приложений: ответ несет
`launchApplicationIds` - что возвращено и что нет. Клиента, запущенного `start_client`, останавливает
`launch_debugger action=terminate`.

`update_database` перед запуском сверяет формат хранимого `ConfigDumpInfo.xml` с форматом, который
записала для этой базы перестройка, и при расхождении отказывает, называя
`sync_control syncOperation=rebuild_dump_info`: на файл чужого формата платформа отвечает `FullDump`, и
обновление становится полной загрузкой. `rebuild_dump_info` (`confirm=true`) перестраивает файл
выгрузкой Конфигуратора самой базы и сохраняет прежний копией; `ignoreDumpInfoFormat=true` пропускает
сверку, `dryRun` сообщает расхождение в `dumpInfoFormatCheck`.
Инкрементальное обновление решается по хранимой копии `ConfigDumpInfo.xml`; рядом с ней лежит
сопроводительный файл `ConfigDumpInfo.record.properties` - для какой базы копия записана и ее отпечаток.
Инкрементальное обновление отказывает с `infobaseChanged` и `nextStep`
(`sync_control syncOperation=rebuild_dump_info confirm=true`), когда копия записана для другой базы
(`recordedInfobase`, `currentInfobase`) и когда базу заменила загрузка `restore_database_snapshot`
(`loadedFrom`, `loadedAt`); `rebuild_dump_info` этот отказ снимает, `fullUpdate=true` копию не читает.
`verifyInfobaseContent=true` (по умолчанию выключен) перед инкрементальным обновлением читает
`ConfigDumpInfo` самой базы запуском Конфигуратора и сравнивает с копией: расхождение - отказ
`infobaseChanged` с `infobaseRecords` и `copyRecords`, неудавшееся чтение - отказ с причиной; копия не
заменяется. Исход сверки - `infobaseChangeCheck` в ответе обновления, `dryRun` и `inspect_database_sync`. `dryRun` отвечает на месте, без
`runKey`: готовность базы и проверку выгрузки он не выполняет и перечисляет в `notCheckedInDryRun`.

С `protectData=true` (по умолчанию) `update_database` до захвата базы сверяет базовую линию синхронизации
(`ConfigDumpInfo.xml`, запись на сущность, сверка по `uuid`) с моделью: удаление объекта или его части,
которое потеряло бы данные, не начинается вовсе - ответ несет `status=confirmationRequired`,
`dataLossTables` (адреса вида `Catalog.X.Attribute.Y`), `dataLossCount`, `dataLossFile`, `dataLossCheck`,
`nothingStarted=true` и `nextStep`. Переименование uuid сохраняет и потерей не считается; базовая линия без
`uuid` или нечитаемое сравнение пропускаются и называются в `dataLossCheck`. `acceptDataLoss=true` проводит
потерю - решение пользователя, а не агента. `inspect_database_sync` (0.2.56) отвечает тем же сравнением,
ничего не запуская: блок `dataLossProtection` с `pendingDataLoss`, `pendingDataLossCount`, `baseline`,
`nextStep`, `dataLossCompared` и `acceptDataLossDefault=false`; настройка `restructureConfirmationPrompt`
(`on` / `off` / `unknown`) только читается.

Свежая привязка базы без базовой линии: `sync_control operation=status` показывает по каждому
приложению проекта, есть ли у его базы базовая линия; `mark_synchronized` с `applicationId` такой базы
записывает базовую линию и ставит на нее идентификатор конфигурации проекта (`configurationUuidStamped`,
при сбое штампа - `stampError`), и следующее `update_database` идет инкрементом.

`export_database_snapshot` / `restore_database_snapshot` (0.2.56) выгружают и загружают всю базу одним
`.dt`. Выгрузка (`path` обязателен) отказывает на существующем файле (`alreadyExists`), а не заменяет его:
дамп пишет один запуск толстого клиента во временный файл рядом с назначением и переносится на место,
только когда непуст и создан этим прогоном (`outputMissing`). Загрузка сначала пишет резервную копию
текущего содержимого базы (`backupTo`, без него - `<имя>-backup-<время>.dt` рядом с файлом; занятый путь -
`alreadyExists`, отсутствующий или пустой исходный файл - `inputMissing`) и без нее не начинается, а после -
заменяет все, что база держит. Обе занимают базу монополией на время прогона (снимки всех баз идут по
очереди), отказ `busy` несет `infobaseHolders`. `timeoutSeconds` 5-120, по умолчанию 30 (псевдоним
`waitSeconds`): дольше - `Pending` с `runKey`; `cancel=true` снимает отслеживание, не прерывая запуск,
ушедший в платформу. Ответ успеха несет `status` (`Exported` / `Loaded`), `path`, `sizeBytes`,
`durationMs`, у загрузки - `backup` с `backupSizeBytes`;
успешная загрузка помечает хранимую копию `ConfigDumpInfo.xml` (`copyMarked: true`,
`infobaseChangeCheck`, `nextStep`), и инкрементальное `update_database` отказывает, пока копию не
перестроит `rebuild_dump_info`; незаписанная пометка - `copyMarked: false` с причиной; прогон, брошенный по бюджету в 600 секунд при
живом процессе, держит блокировку базы - ответ называет `leftBehind` и `lockHeldForProcess`.

`sync_control syncOperation=retrieve_database_changes` (0.2.56) подтягивает изменения базы в проект через
менеджер синхронизации EDT - направление, обратное `update_database`; `applicationId` обязателен, когда у
проекта несколько приложений, у расширения берется база расширяемой конфигурации (`infobaseProject`,
`viaParentProject`). Проект с собственными правками отказывается до `replaceLocal=true` (версия базы этих
объектов заменяет правки проекта); каждый ответ несет `localChanges`, `conflictAsked` и счетчики изменений
базы (`infobaseChangesNew` / `Modified` / `Deleted`). После успешного подтягивания источники объектов,
которых в базе больше нет, снимаются (`removedSources`, `skippedObjects`, `removalFailures`, `filesKept`),
проект перечитывается и ждет сборки; `markSynchronized=true` записывает ту же базовую линию, что
`mark_synchronized` (`baselineMarked=false` с `baselineMarkError` при сбое). Толстый клиент, запущенный
этой EDT, отказывает до платформенного вызова по имени конфигурации запуска (`busy`, `heldBy`);
`timeoutSeconds` 30-3600, по умолчанию 300: дольше - `Pending` с `runKey`, платформенное подтягивание при
исчерпании бюджета не отменяется, свежий вызов без `runKey` начинает заново. Ответ успеха несет `pulled`,
`resolution`, `durationMs`.

`restart_edt` перезапускает EDT с аргументами JVM пользователя и не множит блок `.ini` от перезапуска
к перезапуску; если блок вычесть нельзя, ответ называет это в `vmArgumentsNote`.

### `config_io` - импорт и экспорт

Объединяет `export_configuration_to_xml`, `import_configuration_from_xml`, `export_object`, `export_common_picture`, `export_database_configuration` и `export_database_extension`.

Сюда же относятся два входа для бинарников, и у обоих есть аналог среди скилов набора - выбор зависит
от того, нужен ли на выходе EDT-проект:

- **`import_configuration_from_binary`** принимает `.cf` или `.cfe` одним файлом и разворачивает его в
  НОВЫЙ проект EDT: бинарник грузится во временную базу, выгружается в Designer-XML и импортируется
  оттуда, временная база потом удаляется. Существующее имя проекта отвергается, чужую базу инструмент
  не трогает. Запускает толстый клиент, поэтому нужен доступный runtime платформы, а на большой
  конфигурации занимает минуты. Если проект EDT не нужен, а нужны просто исходники - это `v8unpack-cf`,
  он распаковывает бинарник без платформы. `1c-db-load-cf` сюда НЕ подходит: он грузит `.cf` в базу,
  а не разбирает его на файлы.
- **`unpack_external_binary`** превращает внешнюю обработку или отчет (`.epf` / `.erf`) в Designer-XML,
  который затем скармливается `import_configuration_from_xml`. Нужен, когда файл пришел со стороны и
  проекта под него еще нет. База, названная в `projectName` / `applicationId`, только предоставляет
  процесс Конфигуратора - ее конфигурация не читается и не меняется. Целые конфигурации и расширения
  инструмент НЕ принимает: их конвертация означала бы загрузку в базу поверх того, что там лежит.
  Разобрать `.epf` без EDT и без платформы умеет скил `1c-epf-dump`.


`export_infobase_objects` (0.2.55) выгружает объекты КОНФИГУРАЦИИ БАЗЫ, а не проекта, в иерархический
XML Конфигуратора: `objects` - верхние объекты, формы (`Catalog.X.Form.Y`) и общие формы, `outputPath` -
пустой или несуществующий каталог. Так берется то, что правили в Конфигураторе, для сравнения с
проектом. Медленная выгрузка отвечает `Pending` с `runKey`.

`export_database_configuration` / `export_database_extension` (0.2.56) выгружают ОСНОВНУЮ конфигурацию
базы в `.cf` или названное расширение (`extensionName`) в `.cfe`: занятый `outputPath` отвергается
(`alreadyExists`) без `overwrite=true`, база не в состоянии `EQUAL` (`outOfSync`) - без
`allowOutOfSync=true`, чтобы прежний файл не сошел за результат вызова. Выгрузка идет во временный файл,
результат принимается непустым и новее момента вызова; обе операции синхронные. У обоих импортов из XML
`baseProjectName` называет проект конфигурации, которую расширяет расширение: несуществующий проект -
отказ `projectNotFound` до импорта. `export_object` отвечает `outputMissing`, когда платформа сообщила об
успешной сборке, а `.epf` / `.erf` по `outputPath` не появился: артефакта не существует, что бы ни говорил
отчет сборки.

### `insights` - аналитика конфигурации

Операции: `project_metrics`, `dependency_graph`, `compare_configurations`, `compare_three_way`, `detect_query_anti_patterns`, `generate_health_snapshot`, `impact_analysis`, `object_summary`, `semantic_metadata_search`, `help`.

`compare_three_way` сравнивает открытый проект с новой поставкой И с поставкой, от которой обе произошли, - это и есть обновление на поддержке. Двух сторон там мало: у доработанной конфигурации отличается почти все, а важно, КТО изменил. Отвечает числом узлов, сколькими различаются, сколько односторонних, ИМЕНАМИ измененных объектов на каждой стороне и списком проблем с пометкой блокирующих. Решения по объектам (`decisions`) записываются на сравнение и выгружаются в файл, который EDT читает обратно. **По умолчанию только читает.** `intent=MERGE` применяет решения к проекту - НЕОБРАТИМО; без решений отклоняется, а проверку выполняет само окружение и при блокирующей проблеме останавливается до записи (пройти дальше - отдельное значение `MERGE_IGNORING_PROBLEMS`, не флаг). Поле `merged` говорит, что произошло на самом деле, а не о чем попросили.

Решения проверяются на сравнении (0.2.56): имя, которого сравнение не держит, неизвестное правило и
`CUSTOM_MERGE` отклоняют объединение ЦЕЛИКОМ (`decisionsRefused`), непрочитанное дерево или отсутствие
корня - отказ до объединения. После объединения все затронутые объекты перепроверяются
(`revalidationNote`); узел `UNKNOWN` удерживается `UPDATE_KEEPING_OURS`, корень модуля с методами целиком
не объединяется, `sectionsOffset` листает разделы. Объединение с изменяющим намерением сперва записывает
точку восстановления файлов проекта (`mergeRestorePoint`) и без нее не начинается (`mergeStarted:
false`); точка и возврат покрывают только файлы проекта - база не копируется и не откатывается.

`compare_configurations mode=files` (0.2.56) сравнивает два дампа на диске: `projectName` - путь первого,
`target` - второго (файл или каталог дампа). Ответ несет `failed` и `failedCount` - нечитаемые файлы,
каталоги без листинга и символические ссылки, которые обход не следует; `success:true` при `failedCount`
выше нуля - неполный diff, а не чистый. Многозначная ссылка сравнивается по типам элементов:
`CatalogRef.A`, ставшая `CatalogRef.B`, видна на `level=attribute`.

`describe_db_tables` (доступен и отдельным именем) показывает, во что объект превращается в базе
данных: основную таблицу, по одной на каждую табличную часть, виртуальные таблицы регистра (остатки,
обороты, срезы) с их параметрами, таблицу изменений, перерасчеты регистра расчета. Имена таблиц и полей
отдаются на двух языках, с типами, готовыми к подстановке после `ИЗ`. Звать ДО написания запроса: за
один вызов видно все, что можно выбрать, вместо перебора имен по одному через `validate_query`.

Все операции только читают проект.

Обходы сужаются: `detect_query_anti_patterns` - модулем (`moduleFqn`) и методом (`methodName`),
`project_metrics` - подсистемой (`subsystemName`, с вложенными). Неизвестная цель или селектор, который
не согласуется со `scope`, - отказ с именем, а не обход всего проекта. `dependency_graph` на уровнях
`metadata` и `mixed` не показывает служебные узлы EDT, сводит повторы ребра в одно с `count` и
принимает `edgeKinds` - какие виды связей оставить.

### `security_audit` - аудит безопасности

Операции: `audit_role_rights`, `find_rls_violations`, `sensitive_data_scan`, `help`. Читают проект все, КРОМЕ одной.

`audit_role_rights mode=orphans` - единственная пишущая: перечисляет права роли на объекты, которых в конфигурации больше нет, и при `apply=true` их удаляет. Решение трехзначное - удаляется только то, про что удалось доказать, что объекта нет; неразрешенное перечисляется отдельным списком и не трогается. Под пресетом без права записи `apply=true` отклоняется.

`find_rls_violations` сужается модулем и методом (`moduleFqn`, `methodName`), `sensitive_data_scan` -
модулем или подсистемой (`moduleFqn`, `subsystemName`).

`audit_role_rights objectType` принимает вид метаданных в любом регистре, языке и числе (`Register` - все
виды регистров), неизвестное значение - отказ со списком; `mode=impact` отклоняет имя не-роли и называет
его; `format=markdown` вне `mode=rights` отвечает JSON с `formatNote`. У `find_rls_violations` неизвестный
`roleName` - отказ со списком ролей, роль с нечитаемым `Rights.rights` отвечает `rlsNotDetermined` с
причиной (`rightsNotRead`). Запись прав (`set_role_right`, `set_role_restriction`, шаблоны ограничений)
читает `Rights.rights` с отключенными DOCTYPE и внешними сущностями и отказывает ДО записи на неизвестную
роль, отсутствующий объект, имя роли с точкой, право, неприменимое к виду объекта, и нечитаемую
конфигурацию; новый блок пишется по имени роли и английскому адресу объекта (`Catalog.Товары`,
`Configuration.<Имя>`), блок в русском написании обновляется, а не дублируется. У `sensitive_data_scan`
неизвестное имя в `checks` - отказ со списком, `all` включает все, имена не различают регистр;
`customPatterns` компилируется с `UNICODE_CASE` и `UNICODE_CHARACTER_CLASS` (массив JSON; запятая внутри
`{n,m}` не делит), неразобранный шаблон - отказ с его текстом; словарь имен сопоставляется по целым
словам идентификатора (`Setting` не срабатывает на `tin`); `statistics.omittedBelowSeverityFilter`
называет скрытое фильтром важности.

### `workspace_marks` - метки рабочего пространства

### `git` - репозиторий проекта внутри EDT

Операции: `status`, `branches`, `log`, `commit`, `checkout`, `show_file_changes`, `revert_file`, `create_merge_restore_point`, `restore_merge_point`. Работает через JGit, который среда несет сама: git.exe не нужен, рабочее пространство не угадывается. Репозиторий ищется вверх от каталога проекта, как это делает сам git.

`status` - дерево и индекс против HEAD (`modified`, `added`, `untracked`, `conflicting`, ...) и на сколько ветка ушла вперед или отстала от tracking-ветки; `branches` - локальные ветки, текущая первой; `log` - последние коммиты, `limit` до 100.

`commit` ставит в индекс и коммитит ТОЛЬКО перечисленное в `paths` (через запятую, от корня репозитория); без путей отвергается - add-all здесь нет по правилу `git-safety-rules`. Автор и все пути проверяются до записи в индекс (0.2.56): `.`, `*`, шаблон, каталог, абсолютный путь и выход за корень через `..` отвергаются по имени, удаленный отслеживаемый файл коммитится как удаление, путь, которого нет ни на диске, ни в индексе, отвергается до постановки хоть одного файла. Застейдженное до вызова в коммит не входит; вызов, у которого ни один названный путь не изменен, отвергается, и пути откатываются из индекса. Ответ несет `changes[]` (путь и вид изменения) и `unchanged` для путей без изменений. Автор - `user.name`/`user.email` репозитория, репозиторию без них нужны `authorName` и `authorEmail`. Ветка, привязанная к базе через `branch_infobase`, называется в ответе `boundInfobase`.

`checkout` - `branch` и `createBranch=true` для создания от HEAD. Переход, который перезаписал бы незакоммиченные файлы, отвергается с их списком в `conflicting` и ничего не меняет.

`show_file_changes` читает diff, ничего не записывая: без `filePath` - перечень измененных файлов со
счетчиками строк (не больше `limit`, по умолчанию 50 и не больше 200; общее число в `totalFileCount`,
усечение - `truncated`), с `filePath` - построчный diff между `fromRef` (по умолчанию `HEAD`) и `toRef`
(по умолчанию рабочий каталог); `granularity=method` принимает только один `.bsl` и называет измененные
процедуры и функции.

`revert_file` возвращает один файл к байтам `fromRef` (по умолчанию `HEAD`) с концами строк, которые дал
бы `git checkout` этого пути (`.gitattributes`, `core.autocrlf`), без правила в репозитории - с текущими
файла. `dryRun=true` показывает diff и пишет его даже при открытом редакторе с несохраненными правками -
отвергается только сама запись. Ответ несет `bytesWritten`, `restoredFrom`, `lineEndings`, `fileStatus` и
`indexUntouched` - индекс не трогается. После `.form`, `.mdo` или `.dcs` ответ советует
`revalidate_objects`: модель держит прежнее состояние до перечитывания.

`create_merge_restore_point` записывает точку восстановления файлов проекта без движения HEAD (коммит
под `refs/aiedt/merge-restore/<pointId>`, для проекта вне git - копия каталога) и отвечает `pointId`,
`kind`, `files`, `fileCount`; точка, которую нельзя записать, отвечает `mergeStarted: false`.
`restore_merge_point` (`pointId`, по умолчанию последняя точка проекта) возвращает файлы точки и удаляет
файлы проекта, которых в точке нет (`restoredFiles`, `restoredCount`, `removedFiles`). База не
копируется и не откатывается.

Записи гасятся пресетами под именами `git_commit`, `git_checkout` и `git_revert_file` (через нее же
проходит `restore_merge_point`): под Read-only фасад читает, а каждая запись отвергается до постановки
файлов или их возврата. `create_merge_restore_point` в рабочее дерево не пишет (ссылка в репозитории или
копия каталога проекта), и пресеты ее не выключают. Все три имени вызываемы и напрямую как алиасы операций.

### `docs_lookup` - документация платформы и объектов

Объединяет `get_platform_documentation`, `get_object_help`, `system_enum_values` и встроенную справку фасада.

`system_enum_values` отвечает на вопрос, что можно написать после точки: `ВидДвиженияНакопления` -> `Приход`, `Расход`. Ошибка здесь не ловится редактором - неизвестный член системного перечисления это ошибка времени исполнения. Значения приходят с обоими именами, поле `valuesFrom` называет тип, из которого прочитано (он НЕ совпадает с тем, что спросили: значения лежат на парном типе-менеджере).

`get_object_help` читает встроенную справку объекта конфигурации - те страницы, что открываются
кнопкой "?" в интерфейсе. Отвечает markdown, язык выбирается параметром. Ценность для агента не в

### `yaxunit_tests` - запуск и отладка YAxUnit

Поддерживает обычный запуск и debug-режим. Требует установленного расширения YAxUnit и конфигурации запуска целевой ИБ.

Прогон асинхронный: инструмент опрашивает запуск ограниченное время (по умолчанию 60 секунд) и
отдает отчет в формате JUnit. Если за окно опроса запуск не закончился, ответ будет **Pending** -
это не ошибка, надо позвать тот же инструмент с теми же аргументами еще раз.

`suites`, `tags` и `contexts` (0.2.56) не фильтры - вызов с ними отвергается: они не сужают фильтр
конфигурации запуска. Незавершившееся обновление перед запуском (`updateBeforeLaunch`, по умолчанию true)
отвергает прогон, называя `updateBeforeLaunch=false` способом запустить без обновления.
`reuseRecent=true` (`mode=run`) отвечает прогоном, завершенным за последние пять минут (`cached: true`,
момент завершения в ответе). Завершенный прогон пишет квитанцию: `receiptPath` - JSON в
`run-receipts/yaxunit_tests` каталога состояния плагина (не больше 20 последних, отказ до запуска
квитанции не пишет, недоступный каталог - `receiptError`); ключ, похожий на секрет (`password`, `pwd`,
`scenarioText`), в квитанцию не пишется на любой глубине, внутри списков тоже. `run_yaxunit_tests` -
алиас этого инструмента, объявляющий и отвечающий JSON.


### `naparnik` - вопрос 1С:Напарнику из EDT (0.2.55)

`naparnik operation=status` сообщает, установлен ли 1С:Напарник в EDT и совпадает ли его версия с
1.0.7. `operation=ask` задает ему один вопрос и отдает ответ; вопрос и то, что читают инструменты
Напарника, уходят в сервис 1С:Напарник. Мост выключен по умолчанию (`mcpNaparnikBridgeEnabled`), при
включенном Напарнику доступны только инструменты чтения, пока не включена `mcpNaparnikAllToolsEnabled`.
К инструментам чтения относится поиск по базе знаний сервиса - документации платформы и ИТС
(`mcp__knowledge-hub__` с началом `Search_`, `Fetch_`, `Diff_` или `Get_`; ответ называет их
`allowedServiceTools`). Ответ без текста и без вызовов инструментов - отказ, `conversationId` и
`replyTo` остаются в нем для повтора вопроса; ответ без текста после вызовов инструментов - успех с
`answerEmpty: true`.
Пресеты только-чтения выключают `naparnik`. Это не сервер `1c-naparnik`: тот - отдельный сервис
проверки кода.

### Отказ несет следующий вызов, каталог - класс инструмента (0.2.52)

Отказ, у которого известен следующий шаг, отдает его готовым в `helpHint`: `{"tool": ..., "arguments": {...}}` и рядом деталь. «Проект не найден» - `project_admin operation=list_projects` плюс `suggestedProjectName`, когда открытый проект близок по имени; «владелец не найден» в записи метаданных - `insights operation=semantic_metadata_search` по имени объекта. Вызов из `helpHint` можно отправлять как есть.

`tools/list` публикует `annotations` MCP: `readOnlyHint` и `idempotentHint` у того, что ничего не меняет, `openWorldHint=false` у всего, что не выходит за пределы машины. Класс читается с пресета Read-only; `git` читающий, пока его записи выключены. Публикуются только значения, отличные от умолчаний спецификации, - инструмент с умолчаниями члена `annotations` не несет.

### `edit_metadata` - универсальный конструктор метаданных

Содержит около 160 операций, разбитых на домены:

- объекты и их вложенные элементы;
- специализированные типы метаданных;
- командный интерфейс;
- HTTP- и SOAP-сервисы;
- управляемые формы;
- макеты;
- карта маршрута бизнес-процесса;
- расширения;
- СКД;
- общие пакетные и служебные операции.

Поддерживает `dryRun`, пакетное выполнение и `operation=help`. Полный список следует получать из встроенной справки, поскольку это самая быстро меняющаяся часть API.

Три вещи, которые из общего списка не видны:

- **`extend_object_type`** (с 0.2.26) добавляет тип объекту, ЗАИМСТВОВАННОМУ расширением, со состоянием `Extended`, не трогая унаследованные. Для такого объекта `set_object_type` не подходит в принципе: состав типов заимствованного объекта живет в блоке расширения, а не в обычном свойстве, и `set_object_type` там писал в никуда, отвечая "применено".
- **`operation=help topic=parameters`** (с 0.2.28) отдает полные правила тех параметров, чье описание в схеме сокращено до одной строки. Параметров не убавилось - убавилось прозы в каталоге, который клиент возит с собой в каждой сессии.

- **`copy_object`** копирует объект в другой проект как СОБСТВЕННЫЙ, а не заимствованный. Разница с
  `extension_workshop borrow_object` принципиальная: заимствование ПЕРЕХВАТЫВАЕТ типовой объект,
  копирование его ПОВТОРЯЕТ. Для объекта, который в основной конфигурации уже есть, нужно
  заимствование. Копированием занимается сама EDT, поэтому идентификаторы, неконфликтующее имя,
  членство в подсистемах и описания типов она берет на себя; выбранное ею имя возвращается в ответе -
  оно не обязано совпадать с исходным. Ссылки на объекты, которых в целевом проекте нет, НЕ
  разрешаются, поэтому копию после переноса надо валидировать.

Пакет (`batch=true`, 0.2.56) принимает запись и в строчной форме - имя операции и пары `name=value`;
токен не вида `name=value` отвергается, значение с пробелами требует JSON-формы. Многоязычный синоним в
форме JSON-объекта применяется или отвергается целиком. Провал записи, следующий из того, что прежняя
операция пакета ничего не создала (`dryRun` или ошибка), помечен `derivedFailure` с номером в
`causedByOperation`; остановленный по ошибке пакет говорит это в `stoppedOnError`. Под `dryRun` каждая
запись пакета идет в своей транзакции - запись, которой нужен объект более ранней, падает.

Формы (0.2.56). `create_form` строит управляемую форму генератором форм EDT (движок мастера новой
формы) по владельцу и назначению; когда генератор не справился, вызов отказывает, транзакция
откатывается и формы не остается - `layout=empty` зовется как повтор без генератора и отвечает
`formLayout: empty`. Пустая форма получает на корне свойства генераторной формы (`SaveWindowSettings`,
`AutoTitle`, `AutoUrl`, `Group=Vertical`, `AutoFillCheck`, `AllowFormCustomize`, `Enabled`, `ShowTitle`,
`ShowCloseButton`), `autoCommandBar` (`horizontalAlign=Left`, `autoFill=true`; недостающая панель
создается именем `ФормаКоманднаяПанель`, `id` -1) и пустой `commandInterface` с панелями навигации и
команд; `formScaffolded` в ответе - число поставленных свойств (поле есть, когда поставлено хоть одно), свойство без сеттера на текущей сборке
EDT пропускается. `setAsDefault` ставит свойство по назначению формы (`defaultListForm` для списка и
тому подобное), форма без сеттера попадает строкой в `formSetterWarnings`. Общая форма
(`ownerFqn=CommonForm.<Имя>`) создается через `create_object`, внутренняя форма получает те же
свойства.

`add_form_event_handler` и `add_command_handler` (`writeStub`, по умолчанию true)
дописывают процедуру в область модуля (`ОбработчикиСобытийФормы`, `ОбработчикиСобытийЭлементовШапкиФормы`,
`ОбработчикиСобытийЭлементовТаблицыФормы<Имя>`, `ОбработчикиКомандФормы` или их английские имена) перед ее
закрывающей директивой, без области создают ее в конце модуля на его языке (`stubRegion`,
`stubRegionCreated`); существующая процедура с другой директивой или числом параметров отмечается
`existingProcedureMismatch` и не трогается. `remove_item` (синоним владельца `containerFqn`) отвергает
макет и объект метаданных, называя операцию, которая их удаляет. Условное оформление формы -
`add_form_appearance_rule` (`itemNames`, условие `field`/`conditionType`/`conditionValue`, `appearance`
как у `add_conditional_appearance`), `remove_form_appearance_rule` (по `index` или `field`, внутри групп
условий) и `list_form_appearance_rules` (цвет `#RRGGBB`, шрифт `Face,height[,bold][,italic]`): правила
живут в `ConditionalAppearance.dcssca` рядом с `Form.form`, ошибка записи - `persistWarning`.
`add_form_command_interface_item` разрешает адрес команды в объект `Command` до создания элемента
(`formApiNotFound`, панель не меняется); адреса - те же, что у `commandName`, без учета регистра.
`list_pictures` отдает стандартные картинки версии платформы проекта (`stockPictures`,
`stockExtPictures`, `filter` по обоим языкам; без реестра - `serviceUnavailable`); `StdPicture.<Имя>`
проверяется по нему, русское имя пишется английским. `get_form_screenshot` отказывает при несохраненных
правках редактора формы и ничего не закрывает; `add_field` с путем данных от не-реквизита формы
отвергается со списком реквизитов формы.

Метаданные (0.2.56). `set_task_addressing` пишет `addressingRegister`, `addressingAttributes`,
`mainAddressingAttribute` и `currentPerformer` задачи или задачи связанного бизнес-процесса: недостающий
реквизит адресации создается с типом и измерением записи, без измерения привязывается к одноименному
измерению регистра (нет такого - отказ со списком), каждое свойство перечитывается в той же транзакции.
`create_object` для справочника и документа идет через фабрику мастера; когда она недоступна - через
базовую, и ответ несет `warning` с умолчаниями, которых объект не получил. `qualifierIgnored` -
квалификатор не подошел ни к одному типу состава (`length` у `Number`). Удаление реквизита, на чей путь
данных выходит элемент формы, требует `cascadeForms=true`: элементы снимаются в той же транзакции
(`formItemsRemoved`). `add_predefined_item` пишет `code` по типу кода владельца, занятый и нечитаемый код
отвергаются до записи. `add_template` сверяет `templateType` с литералами модели до транзакции, синонимы
приводятся к литералу (`GraphicalScheme` к `GraphicalSchema`), ответ несет `requestedTemplateType` при
расхождении. `create_route_map` пишет схему маршрута бизнес-процесса (`location`, `handlers`);
обработчику, которого модуль объекта не объявляет, пишется процедура с параметрами события
(`stubsWritten`, при `dryRun` - `stubsToWrite`).

### `dcs_workshop` - схема компоновки данных

Создает и изменяет наборы данных, поля, параметры, связи, вычисляемые поля, ресурсы, настройки и варианты отчета. Проверяет запросы и выражения перед записью.

`repair_schema` (через фасад - `edit_metadata operation=repair_report_schema`) восстанавливает схему из `.dcs` в модель, когда макет в EDT открывается с «Схема недоступна», а файл цел. Доводы: `projectName`, `objectName`, `templateName` (по умолчанию - основная схема владельца на языке конфигурации), `overwriteModel`, `dryRun`. Файл не изменяется. `outcome`: `restored` (в модели схемы не было), `matched` (модель уже совпадает с файлом, ничего не изменено), `refused_model_differs` (в модели другая схема - заменяется только с `overwriteModel=true`, и тогда ее сериализация пишется в `backupPath` рядом с `.dcs`), `replaced`, `file_changed` (файл изменился между чтением и подключением - повторить), `no_template`, `no_file`. `success=true` только при `confirmed=true` - модель после фиксации сериализуется в байты файла, иначе `confirmation` называет причину. `dryRun=true` решает и отвечает, ничего не меняя.

Запись настроек (отборы, параметры данных, варианты) отвечает `settingsWarnings`, если в варианте
остался отбор, сравнивающий с пустым значением (`emptyFilterValue`), или произвольный период без дат
(`emptyPeriod`); запись при этом выполнена.

Детали (0.2.56): `add_field` пишет `title`, `type` и пару `property`/`value` (`property=type` читается как
тип), неизвестное свойство и неприменимый тип отвергаются до добавления. `add_parameter` / `set_parameter`
применяют `length`, `precision`, `fractionDigits`, `nonNegative`, `dateFractions`, `allowedLength` к типу
значения и пишут `expression`, `use` (`true`/`Always`/`Всегда` - Always, `false`/`Auto`/`Авто` - Auto,
иное - отказ), `valueListAllowed`, `denyIncompleteValues`; квалификатор без `type` и неразрешимый тип -
отказ без записи. `set_output_parameter` создает контейнер и запись, имя сверяется с перечнем параметров
вывода платформы (неизвестное - отказ с ближайшим именем; перечень не читался - запись идет, ответ несет
`outputParameterNameChecked: false`). `remove_dataset` снимает вместе с набором вычисляемые и итоговые
поля, в выражении которых имя набора стоит отдельным словом с точкой (`Sum(Sales.Amount)`), без учета
регистра; `remove_query_condition` снимает соседний `AND`/`OR`, условие между `AND` и `OR` отвергается;
неизвестный литерал `comparisonType`, `conditionType`, `orderType`, `groupingType` отвергается со списком
`Allowed:`. `remove_dataset`, `remove_dataset_field`, `remove_parameter`, `remove_calculated_field` и
`remove_total_field` читают все варианты настроек и называют в `affectedSettings` выборку, порядок,
фильтр, структуру, условное оформление и параметры данных, ссылающиеся на удаляемое (сами настройки не
меняются; `reportAffectedSettings=false` список не выводит). `add_settings_table` / `add_settings_chart`
пишут ресурсы схемы в выбранные поля структуры; схема без ресурсов отвечает, что ничего не выбрано.
Настройки динамического списка с `formFqn` и `attributeName` идут в
`Attributes/<имя>/ExtInfo/ListSettings.dcss` (ошибка записи - `persistWarning`).

### `mxl_workshop` - табличный макет MXL

Управляет областями, ячейками, объединением, оформлением, шириной, высотой и рисунками табличного документа. Поддерживает preview через `dryRun`.

`format_cells` задает на диапазоне перенос текста (`textPlacement`), поворот (`textOrientation`), высоту строки, ширину и автоширину колонки и вес колонки при распределении ширины. Формат ищется среди существующих и добавляется, только если такого нет: в `.mxl` форматы общие и адресуются индексом.

`check_print_width` (0.2.55) по модели макета отвечает, поместится ли область печати на лист по
ширине: `verdict` (`fits`, `borderline`, `overflows`, `smallPrint`, `empty`), ширина содержимого и
печатной области в мм, запас. Платформа не запускается, макет не меняется.

Детали (0.2.56): `set_cell` принимает `fillType` и `parameter` и отвергает текст вместе с `parameter`, а
имя параметра - без `fillType=template`; `format_cells` принимает границы, шрифт, цвета, узор и параметры
печати (вызов только с параметрами печати не требует диапазона) и отвергает `fillType` и `parameter`.
`textOrientation` - градусы 0-360, `read_template` отвечает углом в градусах. Нечисловые `borderWidth`,
`scale`, `copies`, `perPage`, `margin` и `margin` вне диапазона `int` отвергаются; `fontSize` и `margin`
принимают дробные. Первый созданный формат пишется в файл макета; смена шрифта берет шрифт, в котором
ячейка отображается (собственный, строки, колонки, формат по умолчанию), связь со стилем сохраняется.

### `extension_workshop` - расширения конфигурации

Объединяет установку, удаление, просмотр и экспорт расширений, lifecycle-сценарии, сравнение с основной конфигурацией и список перехватчиков, а также заимствование: `borrow_object`, `borrow_child`, `borrow_form_item`, `borrow_module`, `borrow_objects`.

Операции над УСТАНОВЛЕННЫМ в базу расширением (`install_extension`, `uninstall_extension`,
`list_extension`) идут через платформу, поэтому у них три условия сразу: доступный runtime,
сохраненные учетные данные (`set_infobase_credentials`) и НЕзаблокированная база - запущенный
клиент 1С держит ее и не дает работать. Удаление расширения из базы разрушительно.
`list_interceptors` и `extension_diff` работают с исходниками расширения и платформы не требуют.

`install_extension` с `updateDatabase` (по умолчанию true, 0.2.56) применяет расширение в базе
(`/UpdateDBCfg -Extension`): `databaseUpdated` ставится только по подтверждению журнала Конфигуратора,
неподтвержденное обновление объясняется в `databaseUpdateNote`, ошибки журнала отвергают вызов
(`databaseUpdateFailed`).


**С 0.2.26 заимствование дописывает связку с типовым объектом** - `extendedConfigurationObject` у корня и в блоке расширения, плюс отметку переопределения модуля. Без нее расширение не переопределяет ничего, а EDT молчит: до этой правки заимствование отвечало успехом, и проект выглядел здоровым. Отсюда три следствия для агента:

- заимствование, которое не смогло дописать связку, **больше не отвечает успехом** - оно называет причину; руками `.mdo` не править;
- **повторный вызов чинит** объект, заимствованный прежней сборкой (раньше второй вызов коротко отвечал "уже заимствовано");
- `borrow_module` **требует `moduleType`** там, где у объекта модулей несколько: у общего модуля отметка лежит в `module`, у справочника - в `objectModule` / `managerModule`, у регистра - в `recordSetModule`. Не назвали вид - отказ перечислит те, что есть.
- `borrow_form_item` заимствует ФОРМУ, которая несет элемент: у элемента формы своего адреса в модели нет. Форму называют доводом `formName` рядом с владельцем либо полным адресом в `objectFqn` (`Catalog.X.Form.ФормаЭлемента`); без названной формы вызов отказывает и не заимствует ничего. То же у `edit_metadata operation=adopt_form_item`, где форму называют `childKind=Form` и `name`.

`borrow_object` с `includeChildren=true` заимствует вместе с объектом его собственные подчиненные
(реквизиты, табличные части с реквизитами, вложенные подсистемы); ответ называет взятых, уже бывших и
пропущенных. В проекте расширения назначение пути данных элементу формы заимствует реквизит основной
формы, с которого путь начинается (`adoptedFormAttributes`); путь, который не будет выгружен с формой
расширения, не записывается.

### `xdto_workshop` - XDTO-пакеты

Создает пакеты, пространства имен, типы объектов, свойства и типы значений XDTO.

### `external_object_workshop` - внешние отчеты и обработки

Создает исходную структуру внешнего отчета или обработки и возвращает созданные артефакты проекта.

`import_external_object` добавляет `.epf` / `.erf` в существующий контейнер: `targetProjectName`, `inputPath`, `baseProjectName` (конфигурация; по умолчанию родитель контейнера), `applicationId` (когда у конфигурации несколько приложений - см. `get_applications`). Бинарник преобразуется через Конфигуратор базы этого приложения, как в `unpack_external_binary`: EDT отпускает базу и берет ее обратно; отказ отпустить - отказ импорта (`infobaseNotReleased`), отказ вернуть - поле `reconnectError` в ответе при любом исходе импорта. Ответ несет `hostProject` и `infobaseName`.

### `support_registry` - реестр поддержки поставщика

Читает, от каких конфигураций поставщика происходит эта, с их релизами, сколько объектов в каждом
режиме поддержки, какие правила среда применит на следующем обновлении, и режим одного объекта
вместе с объектами, которые среда потребует изменить вместе с ним. Операции: `status`,
`list_objects`, `object_mode`, `snapshot_modes`, `restore_modes`, `help`.

Режим - это то, что ОБЪЯВЛЕНО для объекта (`ChangesNotAllowed`, `ChangesAllowed`, `CANCELLED`), а не
утверждение, что объект изменен; на второй вопрос отвечает `compare_three_way`. Расхождение этих
двух и есть опасное место: объект изменен, а режим остался `ChangesNotAllowed` - следующее
обновление поставщика затрет доработку.

`object_mode` принимает адрес потомка (`Catalog.Товары.Attribute.Автор`) и вложенной подсистемы
(`Subsystem.А.Subsystem.Б`); зависимые объекты названы адресами, а не идентификаторами, и страница
берет `offset` и `limit` (`dependentsTotal`, `dependentsShown`, `dependentsMore`). Когда объект
числится в режиме `ChangesAllowed`, а редактировать его нельзя, ответ объясняет расхождение.

`snapshot_modes` записывает в файл, какой объект какой режим держал - этим объединение и делается
обратимым: обновление берет модель поддержки из поставки, и никакое правило объединения этому не
мешает. `restore_modes` возвращает записанное обратно и единственный здесь меняет конфигурацию:
без `apply=true` он только сообщает, что сделал бы. Реквизиты, табличные части и их реквизиты, формы,
макеты, команды и вложенные подсистемы разрешаются по модели и получают записанный режим; запись, которую
внутри транзакции не удалось адресовать или перечитать, названа в `refused` (до 500 имен), полное число
отказов - `refusedCount`, усечение - `refusedTruncated`. `apply=true`, нашедший расхождение и не
восстановивший ничего, заканчивается предупреждением, а не успехом; запись в объект, закрытый записью
поддержки, отвергается тегом `supportLock`.
