# Замеры, мониторинг, полнотекстовый поиск, итоги

Четыре механизма БСП, не участвующих в прикладной логике напрямую, но влияющих
на нее: замеры производительности ключевых операций, отправка обезличенной
статистики, полнотекстовый поиск по данным, управление итогами и агрегатами.

## Модули

| Модуль | Механизм | Контексты |
|---|---|---|
| `ОценкаПроизводительности`, `ОценкаПроизводительностиКлиент` | замеры ключевых операций | сервер / клиент |
| `ЦентрМониторинга` | обезличенная статистика использования | сервер, толстый клиент, внешнее соединение |
| `ПолнотекстовыйПоиск` | обновление индекса и поиск по данным | сервер, толстый клиент, внешнее соединение |

**Модуля `УправлениеИтогамиИАгрегатами` в публичном интерфейсе нет**: механизм
работает регламентным заданием и настройками, а не вызовами из прикладного кода.
Проверено по обеим поставкам.

## Сценарии

### 1. Замерить свою ключевую операцию

**Задача:** понять, сколько занимает проведение документа у реальных
пользователей.

**Функции:**

`ОценкаПроизводительности.ЗакончитьЗамерВремени(КлючеваяОперация, ВремяНачала, ВесЗамера = 1, Комментарий = Неопределено, ВыполненСОшибкой = Ложь) Экспорт`
- процедура, регион `ПрограммныйИнтерфейс`. Сервер.

`ОценкаПроизводительности.ЗакончитьЗамерДлительнойОперации(ОписаниеЗамера, КоличествоДанных, ИмяШага = "", Комментарий = "") Экспорт`
- процедура, тот же регион.

`ОценкаПроизводительности.ЗакончитьЗамерВремениТехнологический(КлючеваяОперация, ВремяНачала, ВесЗамера = 1, Комментарий = Неопределено) Экспорт`
- процедура, тот же регион.

**Нюансы и антипаттерны:**

- Вес замера не декоративен: по нему считается средняя длительность операции на
  разном объеме данных. Замер проведения одной строки и тысячи строк с весом
  единица даст бессмысленное среднее.
- Замер прикладной и технологический идут в разные отчеты. Технологический нужен
  для служебных операций, а не для пользовательских.
- Замер, не завершенный при ошибке, портит статистику. Параметр `ВыполненСОшибкой`
  для этого и есть.

### 2. Записать бизнес-статистику

**Задача:** отправлять в центр мониторинга обезличенный факт использования
механизма.

**Функции:**

`ЦентрМониторинга.ЗаписатьОперациюБизнесСтатистики(ИмяОперации, Значение, Комментарий = Неопределено, Разделитель = ".") Экспорт`
- процедура, регион `ПрограммныйИнтерфейс`. Сервер.

`ЦентрМониторинга.ЗаписатьОперациюБизнесСтатистикиСутки(ИмяОперации, КлючУникальности, Значение, Замещать = Ложь) Экспорт`
- процедура, тот же регион: одна запись в сутки на ключ.

`ЦентрМониторинга.ВключитьПодсистему() Экспорт` - процедура, тот же регион.

**Нюансы и антипаттерны:**

- Статистика ОБЕЗЛИЧЕННАЯ. Класть в имя операции или комментарий данные
  пользователей и контрагентов нельзя: они уйдут наружу.
- Суточная запись существует, чтобы не слать одно и то же событие тысячу раз.
  Обычная запись в цикле раздувает отправку.

### 3. Полнотекстовый поиск по данным

**Задача:** найти объекты по фрагменту текста в любом реквизите.

**Механизм:** модуль `ПолнотекстовыйПоиск`, регион `ПрограммныйИнтерфейс`. Сервер.
Обновление индекса и выполнение поиска.

**Нюансы и антипаттерны:**

- Поиск работает по ИНДЕКСУ, а не по текущим данным. Только что записанный объект
  находится не сразу: индекс обновляется регламентным заданием.
- Не подменять полнотекстовый поиск запросом с подобием по всем реквизитам: на
  большой базе он не завершится.

### 4. Итоги и агрегаты

**Механизм:** настраивается администратором и пересчитывается регламентным
заданием. Публичного программного интерфейса у механизма нет.

**Нюансы и антипаттерны:**

- Не пересчитывать итоги своим кодом при каждом проведении: платформа делает это
  сама, а библиотека управляет расписанием пересчета.
- Отключенные итоги ускоряют запись и замедляют чтение остатков. Это решение
  администратора, и прикладной код на него полагаться не должен.

## Различия версий

Состав модулей всех механизмов в 3.1.11 и 3.2.1 совпадает - сверено по обеим
поставкам.
