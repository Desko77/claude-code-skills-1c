# Синхронизация форка с upstream (sync-fork)

Цель: обновить форк из upstream, не потеряв собственные доработки, либо (режим
parity-check) только сравнить и доложить, что нового. В upstream НИКОГДА не
пушить - он только для чтения (fetch).

## 1. Найти upstream и забрать изменения

- `git remote -v` - найти remote с именем upstream (или иной, указывающий на
  оригинальный репозиторий).
- Если remote нет - спросить у пользователя URL upstream-репозитория и
  добавить: `git remote add upstream <URL>`.
- `git fetch upstream` - забрать изменения. Определить главную ветку upstream
  (main или master): `git remote show upstream`.

## 2. Сводка новых коммитов upstream

`git log --oneline HEAD..upstream/main` - что появилось в upstream и
отсутствует у нас. Сгруппировать по темам (фичи, фиксы, доки, инфраструктура)
и выдать пользователю краткую сводку, а не сырой список коммитов.

## 3. Зона защиты: наши расходящиеся коммиты

`git log --oneline upstream/main..HEAD` - НАШИ коммиты/патчи, которых нет в
upstream. Это зона защиты: кастомизации, которые при слиянии обязаны выжить.
Перечислить их явно (при необходимости с файлами: `git log --stat`).

## 4. Стратегия слияния

Предложить пользователю стратегию, НЕ выполнять слияние без его выбора:

- Работать на отдельной ветке `sync/upstream-<дата>` (например
  `sync/upstream-2026-07-07`), НЕ в main.
- merge upstream/main - сохраняет историю обеих сторон, проще откатить.
- rebase на upstream/main - линейная история, но переписывает наши коммиты.
- НИКОГДА не force-push в main. Кастомизации из зоны защиты (шаг 3) сохранять.
- После слияния и проверки - обычный merge/PR ветки sync в main.

## 5. Конфликты контента

При конфликте по каждому файлу составить таблицу и показать пользователю до
разрешения:

| Файл | Наш патч (что и зачем меняли) | Что изменил upstream |
|------|-------------------------------|----------------------|

Решение по каждой строке (наше / их / объединить вручную) принимает
пользователь, если однозначное решение не следует из контекста доработки.

## 6. Режим parity-check (без слияния)

Триггеры: "сравни с upstream", "parity check", "что нового в мейнстриме" - без
просьбы обновиться. Ничего не сливать и не менять в рабочей копии:

- `git fetch upstream` + сводка коммитов (шаги 1-2).
- Сопоставить новые фичи upstream (по коммитам, релиз-нотам, changelog) с
  нашим бэклогом/доработками.
- Выдать отчет-сравнение: что у upstream уже есть, чего нет у нас
  (gap-список), и что из нашего отсутствует в upstream.

## Правила

- В upstream никогда не пушить (`git push upstream ...` запрещен).
- Деструктивные git-операции - по `~/.claude/rules/git-safety-rules.md`.
