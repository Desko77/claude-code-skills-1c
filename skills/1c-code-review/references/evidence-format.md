# Формат следа проверок

След - машинный журнал прогона проверок: что обязательно (событие `scope`), что
выполнено и с каким итогом (`applied`), что пропущено и почему (`skipped`), что не
измерялось (`not_verified`), жив ли источник (`probe`), что снято человеком (`release`).
Валидатор - `tools/evidence.py` (`check`, `render`); события `skipped`, `not_verified`
и `probe` пишет он же (подкоманда `add`). Записи `applied`, `failed` и `release` пишет
только хук: набрать их через CLI невозможно.

## Каталог событий

`<база>/<ключ>/<session_id>/events/` - вне репозитория, для которого идет прогон.
Идентификатор сессии дает хук `SessionStart` (`hooks/session-context.mjs`):
сообщает модели строку `сессия: <id>` и путь каталога событий через `additionalContext`
(при `source` `startup`, `resume`, `clear`, `compact`, `fork`) и вычищает устаревший
след; командам и инструментам идентификатор передается доводом `--session`.
Допустимые символы идентификатора: буквы, цифры, точка, подчеркивание, дефис;
разделители пути недопустимы.

База: переменная окружения `QUALITY_STATE_DIR`, если она не пустая; иначе
`<домашний каталог>/.claude/state/quality`. Домашний каталог: на `win32` -
`USERPROFILE`, затем `HOME`, затем каталог пользователя процесса; на остальных
платформах - `HOME`, затем `USERPROFILE`, затем тот же каталог.

Ключ репозитория одинаков у `hooks/common/quality-events.mjs` и
`tools/quality_events.py`:

1. `top` - `git rev-parse --show-toplevel`; в `hooks/edt-gate.mjs` при отказе git - `cwd`.
2. Канонический путь: `realpath` (`realpathSync.native` в Node, `os.path.realpath` в
   Python); отказ - `top` без изменений.
3. Нормализация: каждый обратный слеш заменить на `/`; пока длина больше 1, строка
   кончается на `/` и не равна виду `X:/` (буква диска, двоеточие, слеш) - отрезать
   последний символ; на платформе `win32` перевести всю строку в нижний регистр.
   Платформа - `win32`, `linux` или `darwin`.
4. Сегмент - часть строки после последнего `/` (может быть пустой). В сегменте каждый
   символ вне `[A-Za-z0-9._-]` заменить на `_`; последовательность `_` заменить одним
   `_`; срезать с обоих концов символы `_`, `.`, `-`; оставить первые 32 символа;
   снова срезать `_`, `.`, `-` в конце; пустой результат - `repo`. Ключ -
   `<сегмент>-<первые 12 hex sha256 от UTF-8 байтов нормализованной строки>`.
5. Корень следа репозитория - `<база>/<ключ>`.

Lock-файлы и `edt-window.json` лежат в `<база>/<ключ>/<session_id>/`. Кэш `/health` -
`<база>/<ключ>/edt-health.json`.

Очистка (срок 7 дней, вызов из `hooks/session-context.mjs`) обходит каталоги ключей
в базе: удаляет каталоги сессий старше срока по времени изменения, затем удаляет
каталог ключа, если в нем не осталось подкаталогов и каждый файл в нем старше срока.
Ошибка файловой системы на отдельном каталоге пропускает этот каталог.

Хуки и инструменты в рабочем дереве репозитория файлов следа не создают.

Одно событие - один файл `<время>-<номер>-<источник>-<id>.json`:

- `<время>` - локальное время записи, `YYYY-MM-DDTHHMMSS-<миллисекунды>`;
- `<номер>` - 6 цифр монотонной последовательности отметки времени. Номер
  резервируется созданием lock-файла `<время>-<номер>.lock` в каталоге сессии
  (открытие с `O_CREAT|O_EXCL`; занятый номер перебирается дальше, lock-файлы
  остаются как занятые номера). События одной миллисекунды упорядочиваются
  номером по записи, а не по источнику: `applied`, записанный в ту же
  миллисекунду, что `scope`, не выпадает из прогона. Писатель событий на Node
  (`hooks/common/quality-events.mjs`) повторяет ту же схему резервирования и тот
  же формат времени; компоненты имени - локальное время, как у Python-писателя;
- `<источник>` - producer: `profile`, `cli`, `hook`;
- `<id>` - 6 шестнадцатеричных цифр; занятое имя перегенерируется.

Тело - UTF-8 JSON с сортировкой ключей, отступом 2 и завершающим переводом строки.
Python-писатель (`tools/quality_events.py`) пишет во временный файл и переименовывает;
Node-писатель (`hooks/common/quality-events.mjs`) создает финальный файл открытием с
`O_CREAT|O_EXCL` и наполняет напрямую - занятое имя дает `EEXIST` и перегенерацию id,
существующий файл не перезаписывается. Созданный файл не изменяется. Чтение
возвращает события в порядке имен (время в имени самолексикографично). Поврежденный JSON
не поднимает исключение: чтение возвращает для него событие `type=corrupt` с именем
файла и текстом ошибки.

## Общие поля

| Поле | Значение |
|---|---|
| `type` | тип события (таблица ниже) |
| `at` | время записи, ISO 8601 с зоной и миллисекундами |
| `session` | идентификатор сессии |
| `diffHash` | хеш канонического множества на момент записи (`changeset.md`) |
| `producer` | кто записал: `profile`, `cli`, `hook` |

## Типы событий

| Тип | Кто пишет | Назначение |
|---|---|---|
| `scope` | профиль | обязательный состав прогона |
| `applied` | только хук | выполненная проверка с итогом |
| `failed` | только хук | отказ инструмента проверки |
| `skipped` | CLI, профиль | пропуск проверки с классом причины |
| `not_verified` | CLI | неизмеренное измерение с причиной |
| `probe` | CLI | проверка доступности источника |
| `release` | только хук `UserPromptSubmit` | снятие проверки или гейта человеком |
| `baseline` | хук `SessionStart` | базовая отметка сессии (спринт 6) |
| `armed` | хук `PostToolUse` | атрибуция правки инструменту (спринт 6) |

### scope

Пишет `tools/change_profile.py` (`profile-map.md`). Поля: `volume` (`class`, `bslLines`,
`bslFiles`), `files` (пути множества), `archetypes`, `env`, `driver`, `required` -
идентификаторы проверок с указанием среды, `analyzerConfig`, `vendorCopy` (обоснование
кальки типового либо `null`).

### applied

Пишет хук `hooks/evidence-writer.mjs` на `PostToolUse` по факту вызова инструмента
проверки; модель это событие не пишет. Поля: `check` (идентификатор из `required`),
`detector`, `env`, `level` (`semantic`, `static`, `llm`, `project-config`), `target`
(цель из доводов инструмента: путь модуля, FQN; `null` когда недоступна), `toolUseId`,
`inputHash` (sha256 канонического JSON `tool_input`), `responseHash` (sha256
канонического JSON `tool_response`), `outcome` - `status` (`pass` | `findings` |
`error`) и числа находок `critical`, `major`, `minor`. Выполнено не значит пройдено:
любой `applied` с `critical` больше 0 в прогоне проверяется раньше прочих событий той
же проверки и блокирует вердикт до снятия - пропуск с классом либо другое `applied`
без critical его не перекрывают.

Проверка определяется по инструменту и доводам: MCP-инструментам AI-EDT соответствует
`<проверка>@edt`, `syntaxcheck` - `syntaxcheck@configurator`; standalone-имена
`get_project_errors` и `detect_query_anti_patterns` закрывают те же проверки, что
одноименные операции фасадов; у фасадов проверкой является только конкретная операция
(`diagnostics`: `get_project_errors`, `validate_for_export`; `insights`:
`detect_query_anti_patterns`; `revalidate_objects` и прочие операции событием не
закрываются); `ask_1c_ai` и `check_1c_code` закрывают одну проверку `ask_1c_ai@edt`.

Разбор итога по инструменту:

| Инструмент | Итог |
|---|---|
| `validate_query` | `pass` при отсутствии ошибок в ответе, `findings` по строкам ошибок |
| `code_review` | `findings` с числом Critical/Major/Minor по кодам диагностик ответа; важность - из гейтового конфига `assets/bsl-ls-gate.json` (уровень равен важности карточки) |
| `get_project_errors` | `findings`, ошибки валидатора платформы - `critical`, предупреждения - `minor` |
| `validate_for_export`, `security_audit`, `detect_query_anti_patterns` | `findings` по строкам-находкам (важность в ответе не различается, все `minor`), `pass` при фразе чистоты |
| `ask_1c_ai`, `check_1c_code` | уровень `llm`; `findings` при замечаниях, `pass` при их отсутствии |
| `syntaxcheck` | `pass` либо `error` - сломанный синтаксис проверку не закрывает |
| скрипты набора (`Bash`/`PowerShell`) | итог из строки результата скрипта (ниже) |

Итог, который разобрать не удалось, пишется со `status: "unknown"` и полем `raw` -
фрагментом ответа до 200 символов. Валидатор такое событие не принимает (`applied` без
итога): итог не выдумывается, прогон требует повторного вызова или разбора человеком.

#### Строка результата скрипта

Скрипты набора (`bsl-validate`, `query-validate`, `meta-validate`, `role-validate`,
`form-validate` в `skills/*/scripts/`) печатают в stdout одну строку результата:

```
EVIDENCE {"check":"bsl_validate@configurator","ids":["CLIENT-04"],"inputHash":"<sha256>","status":"findings"}
```

`check` - идентификатор проверки со средой, `ids` - карточки-находки, `inputHash` - хеш
входа скрипта, `status` - итог. Хук пишет `applied` по этой строке, только когда команда
запускает скрипт набора (путь `skills/<скил>/scripts/<имя>-validate.ps1|py` либо
`scripts/<имя>-validate.ps1|py` от корня скила) - вывод команды без запуска скрипта
событием не становится; числа важностей считаются по карточкам из `ids` по сводной
`references/detectors.md`. Запуском считается путь скрипта исполняемым токеном команды:
довод `python`/`python3 [-X utf8]`, довод `-File` у `pwsh`/`powershell`, первый токен
команды либо вызов `& "<путь>"`. Путь в комментарии, строковом литерале-аргументе
прочей команды или после `echo` запуском не считается. Известный предел: хук
подтверждает запуск по форме команды, а не по факту процесса - `python -c` с кодом,
печатающим строку `EVIDENCE`, или одноименный скрипт-подделка формой проходят.

### failed

Пишет хук `PostToolUseFailure` (`hooks/evidence-writer.mjs`). Поля: `check`,
`detector`, `toolUseId`, `error`. На `failed` ссылается пропуск класса
`tool_unavailable`.

### skipped

Поля: `check`, `class` и либо `ref`, либо `reason`:

- `tool_unavailable` - инструмент недоступен; `ref` - имя файла события `failed` или
  `probe` со статусом `down` в том же прогоне;
- `not_applicable` - проверка неприменима; `reason` - причина.

Пропуск без `check`, без класса, с неизвестным классом, без `ref` у `tool_unavailable`
или без `reason` у `not_applicable` - невалидный прогон.

### not_verified

Поля: `dimension` (измерение: производительность, поведение в режиме Предприятия и
прочее), `reason`. Вердикт не меняет, попадает в отчет `render`.

### probe

Поля: `source`, `status` (`ok` | `down`), `detail`. Источники: `ai-edt` (инструменты
AI-EDT), `naparnik` (1c-naparnik), `script` (скрипты набора). Вердикты `clean` и
`with_gaps` требуют `probe ok` по каждому источнику, на который опираются закрывающие
`applied`-события:

| Проверки | Источник |
|---|---|
| `code_review`, `validate_query`, `validate_for_export`, `get_project_errors`, `security_audit` | `ai-edt` |
| `ask_1c_ai` | `naparnik` |
| `syntaxcheck`, `bsl_validate`, `query_validate`, `meta_validate`, `role_validate` | `script` |
| `catalog_read:*`, `cross_review`, `adversarial_audit` | не требует probe |

### release

Пишет только хук `UserPromptSubmit` (`hooks/release-writer.mjs`), когда промпт человека -
команда снятия; модель промпты не отправляет, источник всегда человек. Синтаксис:

```
/quality release gate <причина> [--for 30m|2h|1d]
/quality release check <проверка@среда> <причина> [--for 30m|2h|1d]
```

Срок по умолчанию 4 часа. Поля события: `scope` (`gate` | `check`), `check` (для
`scope=check`), `reason` (без `--for`), `source` (`user_prompt`), `expiresAt`
(ISO 8601 с зоной). Действующее снятие: `diffHash` равен текущему и `expiresAt` позже
момента проверки. Снятие `gate` закрывает все обязательные проверки прогона, `check` -
одну. Нераспознанная команда снятия события не пишет, диагностика - в stderr хука.

### baseline и armed

Хуки спринта 6: `baseline` (`head`, `changeset`) - базовая отметка сессии; `armed`
(`file`, `tool`, `toolUseId`) - атрибуция правки. Валидатору достаточно знать тип.

## Прогон

Прогон - последнее событие `scope` с текущим `diffHash` и все события с тем же `diffHash`
после него (порядок - имена файлов). События с другим `diffHash` к прогону не относятся,
кроме `release`: снятие с чужим `diffHash`, найденное в каталоге сессии, и просроченное
снятие - невалидный прогон независимо от прогона.

## Вердикт check --strict

Проверка всегда строгая; флаг `--strict` принят для явности.

- `clean` (код 0): есть `scope` с текущим `diffHash`; каждая проверка из `required`
  закрыта `applied` с итогом `pass` или `findings` без `critical`; есть `probe ok` по
  каждому источнику, на который опираются закрывающие `applied`; пропусков и снятий нет.
- `with_gaps` (код 1): блокирующих условий нет, каждая проверка из `required` закрыта
  одним из трех способов - `applied` (как в `clean`), `skipped` с классом, действующим
  `release`; есть хотя бы один пропуск или снятие.
- `blocked` (код 3): нет `scope` с текущим `diffHash` (прогон устарел или не создан);
  поврежденный файл события; обязательная проверка без события; `applied` с `critical`
  больше 0 без действующего снятия этой проверки либо гейта - такое `applied`
  проверяется первым, и пропуск либо другое `applied` без critical проверку не
  закрывают; `applied` без `toolUseId` или без итога; пропуск без класса или без
  ссылки; `release` с чужим `diffHash` или просроченное; нет `probe ok` по источнику
  закрывающего `applied`.
- код 2 - ошибка вызова (каталог, git, base, идентификатор сессии).

## CLI

```
python tools/evidence.py add --repo <каталог> --session <id> [--base <коммит>]
    --type skipped --check <проверка> --class <tool_unavailable|not_applicable>
        [--ref <файл события> | --reason <причина>]
python tools/evidence.py add ... --type not_verified --dimension <измерение> --reason <причина>
python tools/evidence.py add ... --type probe --source <ai-edt|naparnik|script>
    --status <ok|down> [--detail <пояснение>]
python tools/evidence.py check [--strict] --repo <каталог> --session <id> [--base <коммит>]
python tools/evidence.py render --repo <каталог> --session <id> [--base <коммит>]
```

`add` с типом `applied` или `release` завершается кодом 2 с сообщением "пишет только
хук". `check` печатает вердикт, блокирующие причины и пробелы. `render` печатает
markdown-отчет: вердикт, таблицы "Проверено", "С пробелами" (с классами пропусков),
"Не проверено" (обязательные без события и события `not_verified`); код 0 при любом
вердикте, 2 при ошибке вызова.
