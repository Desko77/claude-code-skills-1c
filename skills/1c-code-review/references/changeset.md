# Каноническое множество изменений (changeset)

Спецификация определяет множество изменений git-репозитория относительно базового
коммита: состав, запись каждого файла, хеш множества и сериализацию. Реализаций две -
`tools/changeset.py` (Python, инструменты набора) и `hooks/_changeset.mjs` (Node, хуки) -
и на одном состоянии репозитория они обязаны давать байт в байт одинаковый JSON и
одинаковый `diffHash`. Тесты `tests/tools/changeset/` сверяют обе реализации на общих
сценариях.

Потребители: профиль правки и валидатор следа, базовая отметка сессии и хуки. Множество
отвечает на вопрос "что фактически изменилось в рабочем каталоге относительно base".
Сравнение выполняет git с учетом `.gitattributes` и `core.autocrlf`, поэтому правка,
вернутая к базовому содержимому, в множество не входит, а хеш содержимого всегда
считается от байтов файла на диске.

## Состав множества

Базовый коммит (base) - любой аргумент, который `git rev-parse --verify <base>^{commit}`
разрешает в коммит; по умолчанию `HEAD`.

Входят:

- измененные файлы - содержимое рабочего файла отличается от base;
- новые файлы - неотслеживаемые (untracked) и добавленные в индекс;
- удаленные - файл есть в base и отсутствует в рабочем дереве;
- переименованные - путь переименован относительно base (обнаружение переименований git).

Не входят:

- игнорируемые файлы (`.gitignore`, `.git/info/exclude`, глобальные исключения);
- подмодули и любой путь, не являющийся обычным файлом рабочего дерева (каталог);
- правка, скомпенсированная возвратом рабочего файла к базовому содержимому
  (в том числе правка в индексе при неизменном рабочем файле);
- файл, добавленный в индекс и удаленный из рабочего дерева (в base его нет);
- изменения настроек и служебных путей git (`.git`).

## Источник данных

`git status` сравнивает только с HEAD и произвольный base не поддерживает, поэтому
каноническая процедура состоит из вызовов git, выполняемых из корня репозитория
(корень дает `git rev-parse --show-toplevel`):

```
git rev-parse --verify <base>^{commit}
git diff --name-status -z -M --no-color --no-ext-diff --no-textconv <base>
git ls-files --others --exclude-standard -z
```

`git diff <base>` сравнивает базовый коммит с рабочим деревом: индексные и рабочие
правки видны одним вызовом, конверсия концов строк применяется по правилам репозитория,
неизмененные файлы не показываются. `git ls-files --others --exclude-standard` дает
неотслеживаемые файлы с учетом всех исключений. Флаги `--no-ext-diff` и `--no-textconv`
отключают внешние и текстовые драйверы diff, если они настроены в конфигурации машины.

Формат записей `git diff --name-status -z`: поля разделены NUL - код статуса, путь; у
R и C после кода идут два пути - прежний, затем новый. Это отличается от
`git status --porcelain=v1 -z`, где у переименования первым идет новый путь.

## Запись файла

| Поле | Значение |
|---|---|
| `path` | путь относительно корня репозитория, прямые косые черты, Unicode NFC |
| `status` | `added`, `modified`, `deleted`, `renamed` |
| `sha256` | SHA-256 содержимого рабочего файла в hex (сырые байты, концы строк значимы); у `deleted` - `null` |
| `renamedFrom` | прежний путь (только у `renamed`), формат тот же, что у `path` |

Чтение рабочего файла выполняется по исходному пути из вывода git (до NFC-нормализации);
в запись пишется нормализованный путь.

## Правила вывода статуса

Первичный статус дают записи `git diff --name-status`:

| Код записи | status |
|---|---|
| `A` | `added` |
| `D` | `deleted` |
| `R<score>` | `renamed`, `renamedFrom` - прежний путь (первый из двух путей записи) |
| `C<score>` | `added` (при `-M` без `-C` не возникает; правило для устойчивости парсера) |
| `M`, `T`, коды конфликта слияния и прочие | `modified` |

Неотслеживаемый путь из `git ls-files --others`:

- пути нет среди записей diff - `added` (в base его нет);
- путь есть среди записей diff (случай `git rm --cached`: файл был в base, из индекса
  убран, на диске остался) - `git diff` такой путь всегда видит удалением (untracked
  для него невидим), поэтому отличие решается сравнением blob-хешей: хеш рабочих
  байтов от `git hash-object --path <путь> <путь>` (фильтры и конверсия пути, как при
  add) против хеша из `git ls-tree <base> -- <путь>`. Хеши совпадают - записи нет,
  различаются - `modified`.

Физическое отсутствие обычного файла в рабочем дереве:

- первичный статус `deleted` или `modified` - запись `deleted` с `sha256: null`;
- первичный статус `added` или `renamed` - записи нет (файла нет ни в base, ни в рабочем
  дереве).

Соответствие классическим кодам `git status --porcelain=v1` (для base = HEAD):

| Код porcelain | status |
|---|---|
| `??`, `A` | `added` |
| `M`, `T`, коды конфликта | `modified` |
| `D` | `deleted` |
| `R` (с `--renames`) | `renamed` |

## diffHash

```
строки = "path\tstatus\tsha256\n" для каждой записи (у deleted вместо sha256 - null),
отсортированные по path побайтово (байты UTF-8, без локали)
diffHash = SHA-256 от конкатенации строк, hex
```

Пустое множество - SHA-256 от пустой строки:
`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.

## Сериализация JSON

```
{
  "base": "<полный SHA-1 базового коммита>",
  "diffHash": "<hex>",
  "files": [<записи, отсортированные по path>]
}
```

Ключи объектов отсортированы, отступ 2, не-ASCII символы не экранируются, после
закрывающей фигурной скобки один перевод строки. Пример (одно переименование, одно
удаление):

```
{
  "base": "3f2a1b0c9d8e7f6a5b4c3d2e1f0a9b8c7d6e5f4a",
  "diffHash": "9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b",
  "files": [
    {
      "path": "docs/readme.txt",
      "sha256": null,
      "status": "deleted"
    },
    {
      "path": "src/module.bsl",
      "renamedFrom": "src/old.bsl",
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "status": "renamed"
    }
  ]
}
```

## Ограничения

- Пути декодируются как UTF-8; невалидный UTF-8 в пути - ошибка, код выхода 2.
- Символическая ссылка на файл не отличается от обычного файла: хешируется содержимое
  по назначению ссылки.
- Настройки репозитория (`.gitattributes`, `core.autocrlf`) влияют на то, что git
  считает изменением; `sha256` при этом всегда считается от байтов файла на диске,
  поэтому один и тот же текст с CRLF и с LF дает разные хеши.

## CLI

```
python tools/changeset.py [--repo <каталог>] [--base <коммит>] [--json]
node hooks/_changeset.mjs --repo <каталог> [--base <коммит>] [--json]
```

Без `--json` печатается таблица для человека (формат таблицы спецификацией не
фиксируется). Экспортируемые функции: `compute_changeset(repo_dir, base)` (Python),
`computeChangeset(repoDir, base)` (Node).

Коды выхода: 0 - расчет выполнен (в том числе пустое множество); 2 - каталог не найден,
не git-репозиторий, git недоступен, base не разрешается в коммит, путь не UTF-8.
