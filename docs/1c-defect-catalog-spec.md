# Спецификация каталога дефектов 1С

Каталог дефектов - данные, а не проза: каждый дефект описан карточкой с фиксированным набором
полей, имеет идентификатор из реестра и фикстуру. Индекс и каталожные секции правил
генерируются из карточек скриптом `tools/gen_catalog_index.py`.

Расположение: `skills/1c-code-review/references/catalog/`.

## Идентификаторы

Формат: `<группа>-<номер>`, номер двузначный, сквозной внутри группы (`PERF-01`, `PERF-02`).

Группы:

| Префикс | Смысл |
|---------|-------|
| `MODEL-` | признаки кода, написанного моделью |
| `PERF-` | производительность |
| `QUERY-` | язык запросов |
| `TXN-` | транзакции и блокировки |
| `FORM-` | управляемые формы |
| `CLIENT-` | клиент-серверное взаимодействие |
| `SEC-` | безопасность |
| `EXT-` | расширения конфигурации |
| `META-` | метаданные |
| `PROC-` | дефекты процесса ответа ("проверено" без следа) |

Идентификатор выдается записью в реестре `catalog/ledger.json` и после вывода из каталога не
переиспользуется. Формат реестра:

```json
{
  "issued": [
    {"id": "PERF-01", "date": "2026-09-21", "title": "Запрос в цикле"}
  ],
  "retired": [
    {"id": "XXX-99", "date": "2026-01-01", "reason": "поглощен карточкой YYY-01"}
  ]
}
```

## Формат карточки

Карточка - файл `<ИДЕНТИФИКАТОР>.md`. Заголовок первого уровня: `# <ИДЕНТИФИКАТОР>. <Заголовок>`.
Разделы второго уровня присутствуют все и строго в этом порядке:

| # | Раздел | Содержимое |
|---|--------|-----------|
| 1 | `## Идентификатор и группа` | строки `Идентификатор:` и `Группа:`; для перенесенных из `anti_patterns.md` - строка `Псевдоним: п.N` |
| 2 | `## Важность` | один из уровней: Critical, Major, Minor (шкала - `severity.md`) |
| 3 | `## Триггер` | что видно в коде или diff; первая строка раздела - формулировка одной строкой для индекса |
| 4 | `## Почему дефект` | последствия |
| 5 | `## Законная форма` | код, где признак триггера присутствует, а дефекта нет. Обязательна |
| 6 | `## Как чинить` | способ исправления |
| 7 | `## Детекторы` | таблица `Среда \| Детектор \| Уровень` из словаря (раздел "Детекторы"); у среды может быть несколько строк, основной детектор первым; при `чтение` в среде EDT обязательна строка `Обоснование чтения: ...` под таблицей |
| 8 | `## Архетипы правки` | подмножество списка архетипов через запятую |
| 9 | `## Фикстура` | строки `Тип:` (bsl-pair, project-tree, diff, evidence) и `Путь:` |
| 10 | `## Источник` | `правило <файл> <пункт>, перенесено <дата>` с дописанным номером `#stdNNN (<заголовок>)`, если стандарт найден через `v8std`, либо инцидент с датой |

Архетипы правки (полный список): транзакция, блокировка, права, запрос, модуль формы,
событие объекта, новый общий модуль, перехват в расширении, изменение метаданных, любой BSL.

Законная форма, отсутствовавшая в исходном правиле, помечается в разделе строкой
`законная форма добавлена <дата>`.

## Детекторы

Словарь детекторов фиксирован; вне словаря детектор в карточке недопустим. Уровень
доказательности назначается словарем и не переопределяется в карточке.

Среда EDT (инструменты AI-EDT и напарник):

| Детектор | Уровень | Что делает |
|----------|---------|-----------|
| `code_review:<КодДиагностики>` | static | внешний bsl-language-server через `code_review`; код - из списка диагностик анализатора |
| `get_project_errors` | semantic | ошибки проекта EDT (валидатор платформы) |
| `validate_query` | semantic | валидация текста запроса парсером платформы |
| `validate_for_export` | semantic | проверки перед записью конфигурации в ИБ |
| `security_audit` | semantic | аудит прав, RLS и чувствительных данных |
| `detect_query_anti_patterns` | static | структурные проблемы запросов |
| `ask_1c_ai` | llm | анализ фрагмента кода внешней моделью (напарник) |
| `чтение` | read | чтение кода ревьюером |

Среда Конфигуратор (формат Конфигуратора без EDT, скрипты скилов набора):

| Детектор | Уровень | Что делает |
|----------|---------|-----------|
| `syntaxcheck` | static | пакетная проверка синтаксиса Конфигуратором |
| `bsl_validate:<ИДкарточки>` | static | правило lint скила `1c-bsl-validate`: регулярные выражения по тексту модуля или запроса; идентификатор правила равен идентификатору карточки. Реализованные правила перечислены в реестре `skills/1c-bsl-validate/scripts/catalog-rules.json`; правило вне реестра в сводной `references/detectors.md` помечается `planned` и в покрытие не входит |
| `query_validate` | static | проверка имен запроса по индексу конфигурации (`1c-query-validate`) |
| `meta_validate` | static | структурная проверка объекта метаданных (`1c-meta-validate`) |
| `role_validate` | static | проверка `Rights.xml` роли (`1c-role-validate`) |
| `form_validate` | static | проверка формы (`1c-form-validate`) |
| `чтение` | read | чтение кода ревьюером |

Уровни доказательности:

| Уровень | Смысл | Детерминированность |
|---------|-------|---------------------|
| `semantic` | семантический анализ модели проекта или платформой | да |
| `static` | текстовый или структурный анализ | да |
| `llm` | анализ внешней моделью | нет |
| `read` | чтение ревьюером | нет |

Правила заполнения матрицы карточки:

- строка таблицы - одна среда и один детектор; основной детектор первым, подтверждающие за ним;
- детерминированные детекторы (`semantic`, `static`) выписываются все подходящие, `чтение`
  в среду EDT добавляется, когда детерминированный детектор признак не закрывает - самого
  детектора нет либо названный в матрице на признаке не срабатывает, - вместе со строкой
  `Обоснование чтения: <причина>`, объясняющей, почему детерминированные детекторы признак
  не закрывают;
- `ask_1c_ai` указывается для признаков, видимых в коде модуля, когда детерминированного
  детектора в EDT нет; для дефектов процесса ответа (`PROC-`) и файлов вне модулей не указывается;
- `bsl_validate:<ИДкарточки>` указывается только для признаков, выразимых регулярными выражениями
  по тексту модуля или запроса без семантики; такие карточки - задание для lint;
- диагностике не приписывается признак, которого она не ловит: сомнение - `чтение` с обоснованием.

Пороги покрытия (проверяет гард `check-catalog.mjs`):

- 100% карточек Critical имеют детерминированный детектор в среде EDT либо обоснование чтения;
- не менее 50% всех карточек имеют детерминированный детектор хотя бы в одной среде; порог
  сравнивается по счетчикам (`покрытых * 2 >= всех`), округленный процент - только печать.
  Детектор `bsl_validate:<ИД>` детерминирован только при `<ИД>` в реестре реализованных
  правил `skills/1c-bsl-validate/scripts/catalog-rules.json`.

Переходное правило (записано 2026-09-22): пока реестр lint-правил пуст, при недоборе порога
50% гард печатает числа и строку "порог покрытия не достигнут: lint-правила не реализованы
(реестр: N из M)" и завершается с кодом 0. С первым правилом в реестре порог проверяется
жестко: недобор - код 1.

Диагностики bsl-language-server, на которые ссылаются карточки, собираются в гейтовый конфиг
`skills/1c-code-review/assets/bsl-ls-gate.json`; состав конфига и ссылки карточек сверяются
гардом в обе стороны. Уровень важности диагностики в конфиге равен важности карточки
(Critical -> CRITICAL, Major -> MAJOR, Minor -> MINOR); одна диагностика с разными важностями
у двух карточек - ошибка каталога.

## Фикстуры

Каталог фикстур: `tests/catalog/<ИДЕНТИФИКАТОР>/`. Манифест `manifest.json` задает тип и
ожидания; файлы фикстуры лежат рядом с манифестом.

| Тип | Файлы | Манифест |
|-----|-------|----------|
| `bsl-pair` | `clean.bsl`, `defect.bsl` | `"type": "bsl-pair"`, `"expected": [номера строк срабатывания в defect.bsl]` |
| `project-tree` | файлы выгрузки (`.mdo`, `.form`, XML) | `"type": "project-tree"`, `"files": [список путей относительно каталога фикстуры]` |
| `diff` | `before.bsl`, `after.bsl` | `"type": "diff"`, `"expected": [номера строк в after.bsl]` |
| `evidence` | `evidence.json` - минимальный след: поле `kind` и описание | `"type": "evidence"`, `"files": ["evidence.json"]`; гард проверяет имя файла (`evidence.json` и только оно), наличие, разбираемость JSON и поле `kind`; полный валидатор следа - спринт 5 |

Модули фикстур - кириллический BSL, 10-30 строк, кодировка UTF-8.

## Генерация

`tools/gen_catalog_index.py` читает карточки, проверяет обязательные поля и пишет:

- `catalog/INDEX.md` - таблица: идентификатор, важность, группа, архетипы, детекторы, триггер
  одной строкой; сортировка по идентификатору;
- `skills/1c-code-review/references/detectors.md` - сводная матрица детекторов (карточка,
  важность, детекторы EDT, детекторы Конфигуратора, признак lint - `lint` либо `planned` по
  реестру реализованных правил) и строка покрытия с двумя числами: детерминированные сейчас
  и с учетом планируемых lint-правил;
- секции между маркерами `<!-- catalog:begin -->` и `<!-- catalog:end -->` в
  `rules/anti_patterns.md` (таблица триггеров с колонкой псевдонима "п.N") и
  `rules/code-review-checklist.md` (таблица по группам с важностью).

Вне маркеров файлы правил скрипт не меняет. Режим `--check` выходит с кодом 1, если
сгенерированное отличается от файлов на диске. Одинаковый вход дает байт в байт одинаковый выход.

## Как добавить карточку

1. Выдать идентификатор записью в `ledger.json` (проверить, что номер группы свободен).
2. Написать карточку по формату, с законной формой.
3. Создать фикстуру `tests/catalog/<ИДЕНТИФИКАТОР>/`.
4. Выполнить `python tools/gen_catalog_index.py` - индекс и секции правил обновятся.
5. Прогнать `node tests/skills/check-all.mjs` - гард `check-catalog.mjs` сверяет карточки,
   реестр, фикстуры и совпадение сгенерированного.
