# Вердикт пакетного запуска платформы 1С

Применяется: при написании и правке любой автоматизации, которая запускает `1cv8.exe` в пакетном
режиме - Конфигуратор (`DESIGNER`), создание информационной базы (`CREATEINFOBASE`), сборку внешних
объектов, проверки конфигурации и расширений.

---

## Код возврата не является вердиктом

Платформа сообщает результат несколькими независимыми каналами, и нулевой код возврата при
проваленной операции - ее штатное поведение, а не сбой. Автоматизация, которая судит об успехе по
коду процесса, принимает провал за успех молча.

Проверка, построенная на таком признаке, не проверяет ничего: она проходит всегда.

## Четыре сигнала

| Сигнал | Как получить | Как читать |
|---|---|---|
| Код возврата процесса | код завершения `1cv8.exe` | не ноль - провал; ноль ничего не доказывает |
| Числовой результат | ключ `/DumpResult <файл>` | в файле число, 0 - успех; не ноль - провал |
| Текст журнала | ключ `/Out <файл>` | классифицируется построчно, см. ниже |
| Постусловие операции | проверка результата на диске | артефакт создан: файл базы, `.cf`, `.epf`, каталог выгрузки |

Порядок сведения:

1. Код возврата не ноль - провал, дальше можно не смотреть.
2. Числовой результат прочитан и не ноль - провал, даже если код возврата нулевой.
3. Числовой результат отсутствует, пуст или не число - сигнал недоступен. Это не провал сам по себе:
   часть операций его не пишет, а в тестовых заглушках его не будет никогда. Отсутствие фиксируется в
   выводе, но вердикт по нему не выносится.
4. Журнал содержит фатальные сообщения - провал операции по существу.
5. Постусловие не выполнено - провал, даже когда все три предыдущих сигнала чисты.

Постусловие обязательно там, где у операции есть материальный результат. Ноль по трем сигналам без
созданного файла - самый дорогой вид ложного успеха: следующий шаг конвейера возьмет файл от прошлого
запуска или упадет далеко от причины.

## Классификация журнала: сначала фразы успеха

Поиск по корням слов "ошибка" и "предупреждение" неверен в обе стороны. Платформа сообщает об
отсутствии проблем теми же корнями:

```
Проверка завершена. Ошибок не обнаружено.
Предупреждений: 0
```

Строка сначала сверяется со списком формулировок, означающих отсутствие проблем, и при совпадении
пропускается. Только потом применяется список фатальных сообщений.

Сверять надо целыми формулировками, а не префиксами. Правило вида "строка начинается с `операция
завершена`" примет за успех строку `операция завершена с ошибками`.

Фатальные сообщения, проверенные на практике:

- `Неверное свойство объекта метаданных`, `не входит в состав объекта метаданных` - реквизит или
  свойство отброшены при загрузке;
- `Неизвестное имя типа`, `Неизвестный объект метаданных`, `Неверное значение перечисления`,
  `не может быть приведен к типу` - ссылка не разрешилась;
- `Ни один из документов не является регистратором для регистра` - регистр остался без движений;
- `необходима версия платформы не меньше` - режим совместимости конфигурации выше установленной
  платформы, база не обновится;
- `Не найден метод` - подпись перехватчика расширения ссылается на метод, которого в конфигурации
  поставщика уже нет;
- `не может быть применен` - расширение не применяется к этой базе.

Список пополняется по мере встреч, но каждое пополнение проверяется парным контролем: набор строк,
которые правило обязано поймать, и набор, на которых обязано молчать. Без второго набора шаблон,
ловящий лишнее, обнаруживается только когда его вывод уже никто не читает.

## Предупреждение на проверочном прогоне

У проверок и у загрузок разная цена предупреждения. На прогоне, который ничего не меняет
(синтаксический контроль, проверка конфигурации, проверка применимости расширения), предупреждение -
это находка: обновление базы с ключом строгого режима отвергнет то же содержимое позже. На загрузке
или выгрузке предупреждение может быть информационным.

Поэтому единого правила "предупреждение это провал" нет. Для каждой операции задается свой список
фатальных сообщений, а повышение строгости выносится отдельным ключом запуска, чтобы поведение по
умолчанию не менялось.

## Устаревший журнал читается как вердикт текущего запуска

Журнал и файл результата пишутся в каталог, уникальный для запуска. Постоянное имя в общем временном
каталоге означает, что при неудачном старте платформы автоматизация прочитает файл прошлого прогона и
объявит по нему успех.

Удаление файла перед запуском проблему закрывает не полностью: два параллельных запуска одного скрипта
затрут файлы друг друга. Уникальное имя надежнее.

То же относится к постусловию: проверять надо не только наличие артефакта, но и то, что он от этого
запуска, если файл мог остаться от предыдущего.

## Пароль в командной строке

Ключ пароля попадает в собранную командную строку, а она обычно печатается перед запуском. Оттуда
пароль попадает в вывод, в журнал сборки и в расшифровку сессии.

Маскировать надо в момент печати, а не в момент сборки аргументов: платформе значение нужно настоящее.
Маскирование покрывает и пароль информационной базы, и пароль хранилища конфигурации.

## Ключи, которые не запускаются из автоматизации

Каждый из них уничтожает состояние, которое ни один из четырех сигналов не восстановит:

| Ключ | Что делает |
|---|---|
| `/EraseData` | стирает данные информационной базы |
| `/DeleteCfg -AllExtensions` | удаляет все расширения базы, включая чужие |
| `/ManageCfgSupport -disableSupport` | снимает конфигурацию с поддержки, необратимо |
| `/IBCheckAndRepair` в изменяющей форме | перезаписывает структуры базы под видом диагностики |

Если задача действительно требует такого ключа, это операция пользователя с его собственной резервной
копией: команда выдается ему на руки, а не выполняется автоматизацией.

## Где это не применяется

В EDT-проекте роль этих проверок выполняет собственная валидация среды, а обновление базы идет ее
средствами. Смешивать два владельца развертывания против одной базы нельзя - см.
`edt-source-format.md`.
