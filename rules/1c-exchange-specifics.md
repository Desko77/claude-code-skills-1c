# Особенности обменов 1С: EnterpriseData, НСИ, межбазовые запросы

Применяется: при разработке обменов - формат EnterpriseData (КД 3.1), обмен НСИ с внешней системой
по HTTP, онлайн-обмен между базами, получение данных из другой базы через веб-сервис.

Правила КД 2.0 и работа с ними через `1c-mcp-toolkit` - скил `kd2-rules`, правила КД 3.1 и расширение
формата - скил `kd31-rules`.

---

## EnterpriseData и собственные пакеты XDTO

- **Тип строки табличной части в расширении формата - всегда отдельный именованный тип**
  (`Документ.X.Товары.Строка`), а не анонимный.
- **Неиспользуемые `<import>` в собственном пакете XDTO** приводят к отказу `XdtoExporter` при
  `update_database` из EDT; Конфигуратор такие импорты разрешает, поэтому применение через
  Конфигуратор проходит.

## Обмен НСИ с внешней системой

- **Соответствия объектов хранить ссылкой (`ЛюбаяСсылка`), а не строкой кода.**
  `Новый УникальныйИдентификатор("00-000043")` завершается ошибкой на строке не в формате UUID, и
  появляются дубли. Образец - регистр БСП `ПубличныеИдентификаторыСинхронизируемыхОбъектов`. Для уже
  накопленных строковых значений - функция "сначала UUID, затем `НайтиПоКоду`".
- **Строка GUID -> ссылка**: `Справочники.X.ПолучитьСсылку(Новый УникальныйИдентификатор(GUID))` в
  `Попытка`.
- **При расхождении спецификации (JSON-контракт) и реальных данных верна версия данных**: регистр
  ключей JSON (`Id` и `id`), имена значений перечислений и выбор "перечисление или строка" не совпадают
  со спецификацией. Имена значений перечислений - из `.mdo`, реальный JSON - из журнала регистрации или
  журнала обмена.
- **Внешний веб-интерфейс может ожидать строковые имена типов в JSON**
  (`attributeType: "Code"`, `entityType: "Regular"`, `action: "Create"`), а не числовые коды. Значения
  перечисления брать из клиентского кода интерфейса, а не из документации.
- **HTTP-сервис: бизнес-ошибки - на языке оператора** (русский для складских систем и ТСД),
  технические идентификаторы - латиницей.
- **Онлайн-обмен периферии с центром без РИБ**: HTTP-сервис на центральной базе и расширение в
  периферийной (подписки на запись, очередь с отложенной отправкой, HTTP-клиент), формат JSON,
  аутентификация по токену.

## Данные из другой базы через CPMDataExchange (УХ)

- **Исходные данные из базы-источника (БП КОРП -> УХ) - через операцию `QueryProcessing`
  веб-сервиса `CPMDataExchange`**, а не через `GetDataForReportRegister`. Параметр операции -
  `ХранилищеЗначения` с текстом запроса (`ТекстЗапроса`) и параметрами (`ИспользуемыеПараметры`),
  результат - `.Получить().РезультатЗапроса`. Запрос выполняется построителем запроса в базе-источнике: `РАЗРЕШЕННЫЕ` не ставить, параметры
  передавать через `ИспользуемыеПараметры`.
- Готовая витрина (табличный документ) - через `GetDataForReportRegister` и
  `Документ.НастраиваемыйОтчет`.
- Запросы к базе-источнику валидировать в проекте ее конфигурации, а не проекта УХ.
