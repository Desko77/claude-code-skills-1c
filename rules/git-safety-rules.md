# Git Safety Rules

Правила безопасной работы с Git. Перед коммитом - кросс-ревью кода другой моделью.

---

## Коммиты

### Авторство
- Никогда не добавлять AI в коммиты (Co-Authored-By, Signed-off-by)
- Коммиты должны отражать реального автора
- В описаниях PR (body, title) не упоминать AI-инструменты (Claude, "Generated with", и т.д.)

### Dangling коммиты на GitHub
- `git push --force` НЕ удаляет старые коммиты с GitHub - они остаются доступны по прямому хешу (месяцами, иногда годами)
- Форки разделяют object store с upstream - dangling коммит форка виден и в upstream по прямому URL
- Единственный надежный способ удалить dangling коммит: удалить форк, пересоздать, запушить чистую историю
- **Вывод: сразу делать коммит правильно, без AI-атрибуции. Исправление постфактум не гарантирует полного удаления.**

### Секреты
Запрещено коммитить: `.env`, `credentials.json`, `*.key`, `*.pem`, `config.local.*`, `*_secret.*`, `tokens.txt`, `passwords.txt`

Если пользователь просит - предупредить о рисках, предложить альтернативы (.gitignore, env.example).

---

## Деструктивные команды

Запрещено без явного запроса:
- `git push --force` / `git push -f`
- `git reset --hard`
- `git checkout .` / `git restore .`
- `git clean -f` / `git clean -fd`
- `git branch -D`
- `git rebase --skip` / `git rebase --abort`

Если пользователь просит:
1. Предупредить о последствиях
2. Показать, что будет потеряно
3. Предложить безопасные альтернативы
4. Запросить явное подтверждение

---

## Force Push

### На main/master - ЗАПРЕЩЕНО ВСЕГДА
- `git push --force origin main` / `git push --force origin master` - НИКОГДА
- Если пользователь настаивает - предупредить о катастрофических последствиях, предложить `git revert`, запросить тройное подтверждение

### На feature ветки - допустимо с осторожностью
- Проверить, что это не main/master
- Проверить, что ветка не shared
- Предупредить и запросить подтверждение

---

## Hooks

Никогда не пропускать без явного запроса:
- `git commit --no-verify` / `git commit -n`
- `git push --no-verify`
- `git commit --no-gpg-sign`

Hooks проверяют качество кода, запускают тесты, проверяют стандарты. Пропуск = обход защиты.

---

## Amend

Использовать `git commit --amend` ТОЛЬКО когда ВСЕ условия выполнены:
1. Пользователь явно запросил ИЛИ pre-commit hook автоматически изменил файлы
2. HEAD коммит создан в этом разговоре (проверка: `git log -1 --format='%an %ae'`)
3. Коммит НЕ отправлен на remote (проверка: `git status` - "Your branch is ahead")

**Если коммит FAILED/REJECTED hook - НЕ amend, создать НОВЫЙ коммит.**
**Если уже pushed - НЕ amend.**
**Если не уверен - НЕ amend.**

---

## Проверки перед деструктивными операциями

1. `git status` - незакоммиченные изменения?
2. `git log --oneline -5` - какие коммиты затронуты?
3. `git branch -a` - на какой ветке? Не main/master?
4. `git remote -v` - куда отправляем?
5. Предупреждение пользователю - что будет сделано, что потеряно, как откатить
6. Явное подтверждение от пользователя

---

## Перед reset/checkout на измененные файлы

1. Показать список файлов
2. Предупредить о потере
3. Предложить: `git stash` / `git commit` / `git branch backup`
4. Запросить подтверждение

## Концы строк (EOL) в 1С-проектах (EDT / Конфигуратор)

Применяется: к любому git-репозиторию с исходниками 1С (EDT `.bsl`/`.mdo`/`.form`/`.dcs`, выгрузка Конфигуратора в XML).

### Симптом

Инструмент сравнения/объединения модулей 1С (Конфигуратор, EDT, внешний diff) показывает расхождения на КАЖДОЙ строке при идентичном коде. Причина - рассинхрон концов строк: одна сторона LF (Unix), другая CRLF (Windows). Кодировка (UTF-8 vs Windows-1251) расхождений НЕ дает - инструмент декодирует обе стороны в Unicode; виноват только EOL.

Корень: EDT нередко пишет `.bsl` в LF, git с `core.autocrlf=true` хранит LF в индексе, а Конфигуратор/ИБ ожидают CRLF. Без явной политики версии расходятся по `\r`.

### Правило

В каждом git-репозитории 1С должен быть `.gitattributes`, нормализующий EOL: репозиторий хранит LF, рабочая копия - CRLF. При работе с git в 1С-проекте (особенно при инициализации репо или диагностике "куча ложных расхождений") - проверить наличие `.gitattributes`; если нет, предложить создать.

Частный случай: после ИМПОРТА из хранилища 1С / загрузки конфигурации БД в EDT git показывает "изменилось все" (каждая строка, отступы). Это НЕ реальные правки, а пересериализация EOL/отступов импортером. НЕ разбирать построчно: проверить `.gitattributes`, затем `git add --renormalize .` и смотреть остаточный diff - он и есть настоящие изменения. Протокол обновления без потери доработок: ДО импорта - WIP-коммит и список своих правок для захвата; ПОСЛЕ - сверка маркеров, возврат затертого, отсев ложного diff.

Эталонное содержимое:

```

*.os text eol=crlf
*.mdo text eol=crlf
*.xml text eol=crlf
*.dcs text eol=crlf

*.cmi text eol=crlf
*.rights text eol=crlf

```

### Диагностика EOL

- `git ls-files --eol <file>` - показывает EOL индекса (`i/`) и рабочей копии (`w/`).
- Точный байтовый счет на диске: `od -An -tx1 <file> | grep -c '^0d$'` (CR) vs `'^0a$'` (LF). CR==LF -> файл CRLF; CR==0 -> LF.
- НЕ использовать `grep $'\r'` в Git Bash для определения EOL - ненадежно.

### Нюансы применения

- При `core.autocrlf=true` индекс уже в LF - массовая ренормализация (`git add --renormalize .`) обычно НЕ нужна, `.gitattributes` лишь закрепляет политику явно и переносимо (не зависит от локального конфига разработчиков).
- Смешанные проекты (1С + Python/Bash-скрипты): обязательно защитить `*.sh`/`*.py` строкой `text eol=lf`. Форс CRLF ломает shebang Bash-скриптов (в Git Bash/WSL) и нарушает конвенцию LF для Python (линтеры, pre-commit).
- Применять только к git-репозиториям с 1С-исходниками (есть `.bsl`/`.mdo`). Не класть в чистые Python/прочие репозитории - там нужна своя политика EOL.
- Долгосрочно: настроить EDT сохранять модули в CRLF (`Window -> Preferences -> General -> Workspace -> New text file line delimiter = Windows`), иначе свежесохраненный в EDT файл снова LF до прокрутки через git.
- Содержимое `.gitattributes` писать без `е` и длинных тире, если того требуют правила проекта (см. `text-formatting.md`).
