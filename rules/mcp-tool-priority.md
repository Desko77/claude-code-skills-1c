# MCP Tool Priority for 1C/BSL

Маршрутизатор: какой сервер брать под задачу. Каталог инструментов AI-EDT (самый крупный и быстро меняющийся)
здесь НЕ дублируется - он в скиле `ai-edt-tools` и его `references/`, потому что две копии каталога уже
расходились. У маленьких серверов набор инструментов помещается в одну строку таблицы и приведен целиком -
отдельного каталога у них нет.

## Выбор сервера

| Задача | Инструмент | Где детали |
|--------|-----------|------------|
| BSL-код, метаданные, формы, запросы, ошибки проекта, отладка, обновление ИБ, юнит-тесты | **ai-edt** (AI-EDT) | скил `ai-edt-tools` + его `references/` |
| API платформы: существует ли метод, сигнатура, типы, конструкторы | **bsl-platform-help** (`search`, `info`, `get_member`, `get_members`, `get_constructors`, `get_platform_info`) | скил `1c-platform-docs` |
| Стиль BSL и строгая типизация | **bsl-platform-help**: `get_coding_guideline` (без параметров), `get_strict_typing_info(topic)` - `topic="topics"` вернет список тем, `search_strict_typing(query)` | в скиле не описаны, параметры здесь |
| Качество BSL, ревью стиля, стандарты ИТС, документация платформы и конфигураций | **1c-naparnik** (`ask_1c_ai`, `check_1c_code`, `review_1c_code`, `rewrite_1c_code`, `modify_1c_code`, `explain_1c_syntax`, `its_help`, `fetch_its`, `search_1c_documentation`, `onec_help`, `diff_1c_documentation_versions`, `config_help`) | скил `1c-naparnik` |
| Функции БСП по описанию задачи | **1c-mcp_ssl_server**: единственный инструмент `ssl_search(query)`, запрос на русском | скил `1c-ssl-patterns` |
| Синтаксис BSL без запущенной EDT | **1c-syntax-checker-mcp**: единственный инструмент `syntaxcheck(code)`, на вход текст кода строкой, НЕ путь к файлу | - |
| Готовый паттерн или шаблон кода | **1c-templates-mcp** (`templatesearch`, `get_template`, `list_templates`, `add_template`, `update_template`, `delete_template`) | - |
| Конфигурация 1С 7.7: объекты, реквизиты, модули, трассировка реквизита | **1c77-metadata** (обязателен для 7.7 вместо ручного парсинга CP1251). ставится отдельно (см. github.com/ivanarama/77MCP), запускается локально на своем порту | скил `1c77-dev` |
| Данные ЖИВОЙ запущенной базы по HTTP, вызов экспортных функций | скил `1c-mcp-toolkit` (обработка `MCP_Toolkit.epf` по HTTP) | сами скилы |
| Журнал регистрации ФАЙЛОВОЙ базы | **ai-edt**: `infobase_admin operation=read_event_log` (читает файлы журнала рядом с базой, платформа не нужна) | скил `ai-edt-tools` |
| Память между сессиями | **hindsight** | правила работы с памятью проекта |

Точные имена MCP-серверов брать из фактически доступных в сессии (`tools/list`), а не по памяти: они
определяются в разных местах - project-scoped `.mcp.json` воркспейса (обычно там `ai-edt`), user-scope
`~/.claude/settings.json` (малые серверы) и подключенные плагины. Ключ `ai-edt` в этих правилах - это
плагин [AI-EDT](https://github.com/Desko77/ai-edt); под другим EDT-плагином имя сервера и набор
инструментов другие, фасадов там может не быть - подставляй фактическое имя и вызывай инструменты по
документации своего плагина. Для Python, TypeScript, Java и прочего
не-1С допустимы обычные инструменты и сторонние серверы.

Для BSL маршрут выше - основной, но не безальтернативный. Разрешенные отступления, каждое с явной причиной:

- **Ошибка `BSL model is not available`** - СНАЧАЛА проверить `modulePath`/FQN: неверный путь дает ровно ту же
  ошибку, и тогда ручной обход не оправдан. Путь верен, модель действительно не построена - точечные `Read` /
  `Grep` по `src/`.
- **1С 7.7** - скил `1c77-dev`; если сервер `1c77-metadata` не поднят, его собственный fallback на
  CP1251-скрипты.
- **Обычные (неуправляемые) формы и конфигурации без EDT-проекта** (формат Конфигуратора) - form-операции
  `edit_metadata` к ним неприменимы; маршрут и fallback на `1c-forms-mcp` описаны в `forms_generation.md`.
- **Инструменты недоступны** - см. раздел ниже, там разные случаи требуют разного.
- **Операция недоступна на этой сборке или сломана** - точечный ручной обход по своду проектных грабель
  (например приведение `.mdo` / `Rights.rights` к эталону) с обязательной перевалидацией объекта после.
  Различать: `*ApiNotFound` и `dcsFactoryMethodNotFound` - это НЕсовместимость runtime, а не дефект, в инбокс
  они не идут (там же уместен GUI-fallback); в инбокс заносится только подтвержденный дефект плагина.

Отступление без одной из этих причин - нарушение правила.

## Когда инструменты недоступны

Одинаковая внешне картина имеет разные причины и разные решения. Не сваливать все в "EDT не запущена".

| Ситуация | Как распознать | Что делать |
|---|---|---|
| Ошибка связи или timeout на `get_edt_version` | транспорт молчит, структурированного ответа нет | Диагноз "ai-edt недоступен". `self_status` НЕ вызывать: он на том же сервере и тоже не ответит; причину не угадывать. "Стоп" здесь означает: не выполнять ИЗМЕНЯЮЩИЕ операции в EDT-проекте и не подменять их ручной правкой - анализ по строке ниже при этом продолжается |
| Сервер отвечает, но операция не проходит | пришел структурированный ответ или осмысленная ошибка | `self_status` (сервер, службы EDT, очередь) - уточнить, что именно не работает |
| EDT не запущена или проект не открыт | `self_status` / сообщение сервера указывают на это | Попросить пользователя запустить EDT. **Изменяющие операции не подменять ручной правкой файлов** |
| Нет EDT-проекта в принципе (Конфигуратор, 7.7) | у задачи другой формат исходников | Уйти на профильный маршрут: `1c77-dev`, `1c-*` скилы формата Конфигуратора, `forms_generation.md` |
| Нужен только анализ и проверка качества, а MCP молчит | задача read-only (ревью, поиск анти-паттернов) | Ручная проверка по `anti_patterns.md` и `code-review-checklist.md` - и продолжить, отметив в отчете, что автоматические проверки не выполнялись (`1c-coding-standards.md`, Fallback) |

Правило разделения: **читать и анализировать без MCP можно, писать в проект вслепую - нельзя.** Запись BSL,
правка метаданных и форм, обновление ИБ в EDT-ПРОЕКТЕ при недоступной EDT не выполняются ручным обходом -
работа останавливается с объяснением пользователю.

Это не запрет писать код там, где EDT нет по определению. Конфигурация 8.x в формате Конфигуратора
(XML-выгрузка, `.epf`/`.erf`/`.cf`/`.cfe`) правится профильными скилами: конфигурация - `1c-cf-*`,
**расширения - `1c-cfe-*`** (borrow / patch-method / diff / validate / full-cycle), внешние обработки и
отчеты - `1c-epf-*` и `1c-erf-*`, объекты и формы - `1c-meta-*` и `1c-form-*`, распаковка бинарников -
`v8unpack-cf`. Это ее штатный маршрут, а не обход. 7.7 - `1c77-dev`. Запрет касается только подмены
недоступных инструментов EDT ручной правкой файлов EDT-проекта.

## Обязательные проверки

**Область действия: EDT-проект 1С 8.x.** Для 7.7 действуют проверки скила `1c77-dev` (в частности
`validate_query` сервера `1c77-metadata`), для конфигураций без EDT - проверки профильных скилов
(`1c-cf-validate`, `1c-form-validate`, `1c-meta-validate` и другие). Пункты ниже применяются к тому
маршруту, который выбран по таблице выше, а не требуют инструментов EDT там, где их нет.

1. **`validate_query` (ai-edt) сразу после каждого написанного или измененного запроса.** Не откладывать и
   не группировать. Для СКД - `dcsMode=true`.
2. **`ask_1c_ai` (1c-naparnik) после изменения BSL** - до 2 итераций на один фрагмент, дальше не крутить.
   Порядок итерации: получить замечания -> **проверить каждое по факту** (существование метода - через
   `bsl-platform-help` или исходники БСП, поведение - через код проекта) -> исправить только подтвержденное ->
   контрольная проверка. Напарник дает false positives и выдуманные API,
   поэтому правка по его замечанию без проверки запрещена. Сервер недоступен или ответил ошибкой - работу не
   блокировать, но явно написать в отчете, что проверка качества не выполнена.
3. **BSL пишется через `write_module_source` (ai-edt)**, а не Edit/Write по `.bsl`: иначе EDT не увидит
   правку до refresh и теряется авто-валидация. Подробности - `edt-bsl-write-safety.md`.
4. **Управляемые формы EDT-проекта правятся form-операциями `edit_metadata` (ai-edt)**, а не ручным XML в
   `.form`. Сервер `1c-forms-mcp` в EDT-стеке отключен: на EDT-проектах давал формы хуже и с ошибками.
   Исключение - обычные формы и конфигурации без EDT (формат Конфигуратора): там маршрут и условия включения
   `1c-forms-mcp` заданы в `forms_generation.md`.
5. **Диагностика после изменений - в таком порядке:** сперва `diagnostics operation=revalidate_objects` по
   затронутым FQN (перевалидировать), затем `diagnostics operation=get_project_errors` с фильтром по ним
   (прочитать результат). Один вызов вместо двух не заменяет другой: без перевалидации ошибки останутся от
   прошлого состояния. `check_1c_code` и `review_1c_code` (1c-naparnik) - не обязательны, а по
   необходимости: первый когда нужен разбор синтаксиса и логики фрагмента, второй когда нужно ревью стиля
   против стандартов ИТС.
6. **`validate_for_export` (ai-edt) перед записью конфигурации в ИБ и сборкой артефактов**:
   `update_database` (включая неявный - у `yaxunit_tests` при `updateBeforeLaunch`, который по умолчанию
   `true`), экспорт в XML через `config_io`, `export_object` / `export_extension`. Findings блокируют
   операцию: сперва исправить, потом обновлять. Проверка ловит класс "валидно в EDT, падает в ИБ" -
   реальные check-id: `mdo-empty-datevalue-fillvalue`, `mdo-empty-numbervalue-fillvalue`,
   `mdo-duplicate-xmlns`, `form-handler-no-event`, `form-empty-action`, `form-command-handler-type`,
   `mxlx-bare-fontstyle`, `dcs-abstract-setting-item` и другие. Проверки на пустой `stringQualifiers` в этом
   инструменте НЕТ - не ссылаться на нее.

## Не выдумывать имена инструментов

Имя инструмента берется из каталога скила или из встроенной справки сервера (`operation=help` у фасадов
ai-edt), а не по памяти и не по аналогии. Проверено на практике: правила и скилы годами носили имена вроде
`search_ssl`, `check_syntax`, `get_function_info`, которых на серверах нет и не было - агент уходил в
несуществующий API. Инструмент не найден - сперва сверить имя с каталогом, потом уже искать обход.

AI-EDT консолидирует инструменты в **фасады**; основные - `code_search`, `edit_metadata`, `diagnostics`,
`launch_debugger`, `project_admin`, `infobase_admin`, `config_io`, `insights`, `security_audit`,
`docs_lookup`, `workspace_marks`, `yaxunit_tests`, `extension_workshop`, а также мастерские `xdto_workshop`,
`dcs_workshop`, `mxl_workshop`, `external_object_workshop` и `external_data_source_workshop`. Полный перечень
с составом операций - `skills/ai-edt-tools/references/facades.md`.

**Синтаксис вызова.** Под пресетом Canonical в `tools/list` видны фасады, а поглощенные ими standalone-имена
скрыты (хотя и остаются вызываемыми). Поэтому канонический путь - фасад с `operation`: не `get_project_errors`,
а `diagnostics operation=get_project_errors`; не `debug_launch`, а `launch_debugger action=launch`. В этом
правиле и в скиле имена операций пишутся короткой формой для узнаваемости - вызывать их следует через фасад,
если standalone-имени нет в `tools/list`. Соответствия по отладке (там имена не совпадают: `set_breakpoint` ->
`action=add_breakpoint`, `evaluate_expression` -> `action=evaluate`, `terminate_launch` -> `action=terminate`) -
таблица в `skills/ai-edt-tools/references/workflows.md`, полный список - `launch_debugger action=help`.

`sync_control` - особый случай: у него собственный набор `operation` (`status`, `diagnose`, `suppress`,
`mark_synchronized`, `reseed_baseline`), который сталкивается с routing-параметром фасада. Через фасад он
доступен, но действие передается ОТДЕЛЬНЫМ параметром: `infobase_admin operation=sync_control
syncOperation=status`. Прямой вызов `sync_control operation=status` проще и потому предпочтителен.

**Когда фасад не подходит.** Фасады (`infobase_admin`, `code_search`, `diagnostics`) отвечают markdown-текстом.
Нужен типизированный JSON (`structuredContent`) для программного разбора - вызывать standalone-инструмент
напрямую; это осознанный размен, заложенный в самом плагине.

Поглощены НЕ все: `write_module_source`, `validate_query`, `get_edt_version`, `read_module_source`,
`read_method_source`, `get_module_structure`, `list_modules`, `ai_context`, `diff_module`, `get_form_structure`,
`get_form_screenshot`, `code_review` и другие остаются самостоятельными - фасада у них нет, вызывать по имени.
Список не исчерпывающий: сверяться с `tools/list` и `references/facades.md`.

**У AI-EDT нет доступа к данным информационной базы - ни в отладке, ни вне ее.** Инструменты `browse_data`,
`execute_query` и объединявший их фасад `data_access` из плагина удалены; в старых заметках их имена еще
встречаются, но вызов вернет «unknown tool». Единственный маршрут к данным живой базы - скил
`1c-mcp-toolkit` (обработка по HTTP). Приостановленная debug-сессия дает состояние исполнения текущего кадра
(`get_variables`, `set_variable`, `evaluate_expression`), то есть переменные и выражения, а не таблицы базы -
подменять этим запрос к данным нельзя.

**Но ЖУРНАЛ РЕГИСТРАЦИИ файловой базы читается прямо из плагина** (с 0.2.27):
`infobase_admin operation=read_event_log` - кто входил, что проводилось, какие обновления платформа
отвергла, с отбором по `from` / `to` / `event` / `user` / `severity`. Это не запрос к данным: журнал лежит
файлами рядом с базой и читается без платформы. Серверная база (журнал на сервере) и однофайловый
SQLite-формат `1Cv8.lgd` отвечают ИМЕНОВАННЫМ отказом, а не пустым списком, - пустой список над базой,
полной событий, читался бы как «событий нет». Свободный текст проходит через маскирование, и ответ прямо
говорит, что маскируется только то, на что у библиотеки есть образец.

## Перед ручным обходом - проверить, что фича уже есть

Типовая ошибка: агент городит правку `.mdo`/`.form` через Write, Python-скрипт или десятки парных вызовов
там, где в плагине уже есть готовая операция. Порядок: `edit_metadata operation=help` (каталог),
`operation=help topic=availability` (что доступно на runtime), профильный фасад или `*_workshop`. Массовое
создание однотипных объектов - `edit_metadata batch=true` с массивом `operations` (38 ролей = ОДИН вызов, не
38 пар). Batch не отменяет валидацию, а сдвигает ее: внутри батча диагностики между операциями нет и
атомарности тоже (каждая операция в своей транзакции), поэтому после вызова разобрать `batchResults[]`,
довести упавшие элементы поштучно и прогнать `revalidate_objects` -> `get_project_errors` по созданным
объектам. Там, где важна проверка ПОСЛЕ КАЖДОГО шага (правка существующих объектов, рискованные операции),
batch не применять.

## Экономия контекста

Результаты MCP-вызовов оседают в контексте до сжатия. Тяжелые выборки (широкий поиск по коду,
`find_references` по якорному объекту, `ai_context depth=full`, большие выборки данных, объемные `recall` и
`its_help`) уводить в субагента - он вернет выжимку, сырье останется в его контексте.

Наследование MCP субагентом - поведение клиента, оно меняется между версиями, поэтому **не полагаться на
память, а начинать делегирование с пробного вызова** (`get_edt_version` для `ai-edt`) в самом субагенте: не
ответил - вести разведку инлайн. Это касается любого типа субагента; у Explore и Plan tools-список урезан и
MCP-серверы отфильтровываются чаще. Историческая заметка: на `general-purpose` наследование, включая
project-scoped `ai-edt`, подтверждалось живыми вызовами 2026-07-07. Живой вызов в любом случае требует
запущенной EDT. Модель субагента под BSL-разведку - Sonnet или выше, никогда Haiku (`model-selection.md`).

Крупные карты (`list_modules`, каталог FQN, структура большого модуля) кэшировать один раз в
gitignored-файл проекта, а не перезапрашивать.

## Троттлинг и ошибки

Не ретраить вслепую: читать тег и текст ошибки. **Цикл редактирования - работа над ОДНИМ объектом или
модулем до его успешной валидации**; переход к следующему объекту сбрасывает счетчики. `syntaxcheck` не более 3 за цикл,
`revalidate_objects` не более 2, `templatesearch` не более 2 разных запросов. После 2 неудачных попыток
исправить ОДНУ И ТУ ЖЕ ошибку одним подходом - сменить подход; не виден и он - остановиться и спросить
пользователя. Останавливается текущий подход, а не вся задача: остальные независимые части доделать и
сказать, что осталось. Полная таблица сигналов (`Pending`/`runKey`,
`propertyMismatch`, `requiresCascadeForms`, `*ApiNotFound`, `BSL model is not available`), грабли больших
конфигураций и `sync_control` - в скиле `ai-edt-tools`, файл `references/gotchas-and-errors.md`.
