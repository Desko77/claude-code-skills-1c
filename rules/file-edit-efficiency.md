# File Edit Efficiency

Стратегия минимизации токенов при чтении и редактировании файлов.

Применяется: при любых операциях чтения/редактирования файлов.

---

## Выбор инструмента по задаче

### Массовые однотипные замены (N файлов, одинаковый паттерн)

**Grep → sed → grep** (всё через Bash):
1. `grep` — найти текущие значения, убедиться в паттерне
2. `sed -i 's|old|new|'` — заменить во всех файлах за один вызов
3. `grep` — проверить результат

Не использовать Read+Edit для каждого файла — Read загружает весь файл в контекст, Edit требует предварительный Read. На N файлах это 2N вызовов и весь контент в контексте.

### Точечные правки (1-2 файла, нужна точность)

**Read → Edit**:
- Edit проверяет уникальность old_string — безопаснее чем sed
- Read нужен один раз, потом можно делать несколько Edit по тому же файлу
- Для больших файлов: Read с offset+limit вместо полного чтения

### BSL-код в EDT-проектах (при наличии MCP)

**MCP read_method_source → write_module_source**:
- Читает/пишет конкретный метод, а не весь модуль (экономия на файлах 3000+ строк)
- write_module_source проверяет синтаксис автоматически
- Режимы: searchReplace, replace, append

### Поиск информации

| Задача | Инструмент | Не использовать |
|--------|-----------|-----------------|
| Найти файл по имени/паттерну | Glob | Bash find, Agent |
| Найти строку в файлах | Grep | Bash grep/rg, Agent |
| Прочитать конкретный фрагмент | Read (offset+limit) | Read всего файла |
| Понять структуру большого модуля | MCP get_module_structure | Read всего файла |
| Широкий поиск по кодовой базе | Agent (Explore) | Серия Grep вручную |

### Кликабельная ссылка на файл (Cursor/VSCode)

**Предпочтительный способ - формат `@-references`:** `@путь/от/корня/workspace/файл.ext:начало-конец`. Работает с кириллицей, не тратит токены на tool-вызов.

Примеры:
- `@src/CommonModules/МодульИмя/Module.bsl:1-1`
- `@ПСБ_ЗУП/src/Catalogs/Контрагенты/ObjectModule.bsl:45-60`

**Когда `@-references` не подходит** (путь вне workspace, например `C:\Users\...`) - fallback через tool-результат:

| Задача | Инструмент | Токены |
|--------|-----------|--------|
| Просто путь к файлу | `Glob pattern="имя_файла"` | ~20-40 |
| Путь + факт совпадения | `Grep output_mode=files_with_matches` | ~20-40 |
| Путь + конкретная строка | `Read file_path=... limit=1 offset=<N-1>` | ~40-80 |

Markdown-ссылки `[текст](путь)` в чате ломаются при кириллице из-за percent-encoding - не использовать.

Антипаттерн: Read полного файла (30000-50000 токенов) только ради кликабельного пути. Между Glob/Grep и Read limit=1 разница пренебрежимо мала, выбор по задаче.

## Кэширование больших карт в файл проекта

Если одни и те же крупные срезы нужны многократно за сессию (карта проекта, список модулей, каталог FQN, структура большого модуля) - сохранить результат ОДИН раз во временный markdown в проекте и работать с ним, не перезапрашивая MCP.

- Подходит для: `get_module_structure` больших модулей, `list_modules`, `get_metadata_objects` по конфигурации, `find_references` по якорным объектам рефакторинга.
- НЕ подходит для: `get_project_errors` (быстро устаревает после правок), результаты отладки, `get_form_screenshot`/`get_form_structure` (зависят от состояния редактора).
- Класть под gitignored-путь (например `.cache/edt-mcp/<имя>.md`). Не коммитить такие снимки.

## Антипаттерны

- **Bash cat/head → Edit**: Edit требует именно Read, чтение через Bash не засчитывается
- **Read всего файла (5000 строк) для одной строки**: использовать Grep или Read с offset+limit
- **Agent (Explore) для простого grep**: Grep/Glob быстрее и дешевле по токенам
- **Последовательные Read N файлов для однотипной замены**: один вызов sed через Bash
- **Read + Write для замены одной строки**: Edit отправляет только diff, Write — весь файл
