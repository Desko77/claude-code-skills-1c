# Известные ошибки EDT: запись метаданных, деплой, хранилище

Применяется: при работе с EDT-проектом через AI-EDT (`ai-edt`) - запись кода и метаданных, валидация,
`update_database`, выгрузка, обновление из хранилища.

Сигналы ответов плагина, троттлинг, большие конфигурации и `sync_control` описаны в скиле
`ai-edt-tools` (`references/gotchas-and-errors.md`) и здесь не повторяются. При расхождении верна
версия скила: она соответствует выпуску плагина. Ошибка `zip:///` - `edt-zip-export-pitfalls.md`,
целостность `.mdo` (UUID, длина строки, `scale`, `fillValue`, `stringQualifiers`) - `1c-mdo-integrity.md`.

---

## Запись метаданных и валидация

- **"Валидно в EDT, ошибка в ИБ" - отдельный класс дефектов.** `get_project_errors` пуст, а
  `update_database` завершается ошибкой (XDTO, реструктуризация): статический валидатор EDT не проверяет структурные
  и XDTO-ошибки. После генерации форм, макетов, СКД и метаданных выполнять реальный `update_database`,
  а не только валидацию.
- **Инкрементальная загрузка ИБ перечитывает только новые и измененные объекты.** Давний дефектный
  объект не дает ошибки, ошибки дают свежеизмененные - это сужает поиск причины.
- **EDT не подхватывает внешние правки `.dcs`, `.mdo`, `.form`** (Python, Bash, `git checkout`) в
  модель сборки без `clean_project` или обновления проекта - деплоится прежняя версия. Схемы и
  метаданные при переносе переносить отдельно от BSL и проверять, что EDT перечитал файл.
- **Запись `.bsl` скриптом с `newline=""` меняет концы строк.** Python читает файл с universal
  newlines (CRLF -> LF), и запись без преобразования сохраняет LF в проекте с политикой CRLF; EDT
  показывает ложные синтаксические диагностики на строках, идентичных рабочим. Писать с
  `newline="\r\n"`, затем `clean_project`. Штатный путь записи BSL - `edt-bsl-write-safety.md`.
- **`dryRun=true` у form-операций проверяет откат транзакции, а не результат на форме.** Ответ
  сообщает успех с откатом при любом содержимом; функциональная проверка - вызов без `dryRun`.
- **Реквизит регистра без `<type>`**: первая запись в регистр разрывает соединение сеанса. После
  создания реквизита проверять, что тип записан в `.mdo`.
- **Поле `CheckBoxField`, привязанное к реквизиту не типа `Boolean`**, ломает отрисовку и загрузку в
  ИБ. Для числовых и перечислимых реквизитов - `RadioButtonField` или переключатель (`Tumbler`).
- **BLOCKER `common-module-type` означает неполный набор флагов общего модуля.** Проверка берет
  ожидаемый вид модуля из суффикса имени; модуль без суффикса проверяется как серверный, а он по
  стандарту 469 требует трех признаков: `<server>true</server>`,
  `<clientOrdinaryApplication>true</clientOrdinaryApplication>`, `<externalConnection>true</externalConnection>`.
  Модуль, созданный `edit_metadata createObject`, несет только `server=true`. Исправление - привести
  набор признаков к соседнему модулю того же вида, суффикс имени не менять. Клиент-серверный модуль
  (суффикс `КлиентСервер`) несет тот же набор плюс `<clientManagedApplication>true</clientManagedApplication>`.
  Перед созданием общего модуля прочитать `.mdo` соседнего модуля нужного вида и повторить набор.
  Отсутствие булева признака в `.mdo` означает `false`: EMF не сериализует значение, равное
  умолчанию, поэтому `set_object_property ...=false` файл не меняет, и это не дефект.
- **Ложные диагностики EDT на больших конфигурациях (УХ, ERP):** `undefined-variable [Толстый
  клиент]` в модуле объекта, синтаксические ошибки после правки формы (кеш маркеров, частичный
  индекс). Проверка платформой надежнее; не исправлять код до воспроизведения ошибки.

## Большие конфигурации

- `clean_project` на конфигурации в тысячи объектов не завершается: вызов отказывает по таймауту,
  проект остается в состоянии `building`, `get_project_errors` отвечает "Project is building" до
  перезапуска EDT пользователем. Файлы на диске при этом сохраняются. Вместо него - `revalidate_objects`
  по FQN измененного объекта.
- `revalidate_objects` на такой конфигурации даже по нескольким FQN может завершиться таймаутом:
  перевалидация продолжается в фоне, и следующий `get_project_errors` тоже отказывает по таймауту.
  Перевалидацию не вызывать после каждой записи: на каждую запись - синтаксическая проверка
  `write_module_source`, после серии правок - один `revalidate_objects` по измененным FQN и
  `get_project_errors` с фильтром по ним.

## NPE EDT при деплое

| Сообщение | Исправление |
|---|---|
| `table is null`, файл `.aindex` | удалить `.aindex` |
| `CommandHandler handler is null` | у команды формы расширения потерян `<action>`: восстановить по `BaseForm`. В расширении контейнер `FormExtensionCommandHandlerContainer/handlers` (множественное число), в основной конфигурации - единственное; имя обработчика - исходное, без префикса |
| ссылка на неизвестный предопределенный элемент, `ExportException EObject`, `WsDefinitions.wsdl` | полный деплой (Clean) после обновления проекта из хранилища |

## Реструктуризация БД и загрузка в ИБ

- **Реквизит типа `Date`**: значение заполнения - `fillValue core:DateValue` с минимальной датой, а не
  `UndefinedValue`, иначе NPE при экспорте.
- **Новый `AccumulationRegister` без документа-регистратора** проходит валидацию EDT, а
  `update_database` отказывает: "ни один документ не является регистратором". Для заполнения
  обработкой или миграцией - `InformationRegister` с `writeMode=Independent`.
- **Экспорт `.cf` из EDT завершается ошибкой на `<help>` без файла `Ext/Help/ru.html`** (типично для объектов
  БСП) - убрать `<help>` из `.mdo`.
- **Расписание регламентного задания в EDT - отдельный файл `Schedule.schedule` рядом с `.mdo`**, тег
  `<schedule>` внутри `.mdo` игнорируется. `repeatPeriodInDay` задается в секундах.
- **Файловая ИБ: перед `update_database` закрыть сеанс 1С** (`ЗавершитьРаботуСистемы(Ложь, Ложь)`),
  иначе "Проект в процессе объединения". На удаленной машине сеанс закрывается внутри сеанса
  удаленного рабочего стола.
- **Внешние обработки БСП (`ДополнительныеОтчетыИОбработки`) хранят двоичный файл в справочнике**, а
  не берут его из каталога сборки: после правки `.epf` - "Загрузить из файла" в карточке.

## Кеш рабочего процесса сервера (rphost)

`rphost` кеширует регламентные задания и сигнатуры функций общих модулей. После переименования модуля
задание отказывает "Метод задания не найден: Старый:Метод" (двоеточие в тексте - норма), после смены
сигнатуры - "Слишком много фактических параметров". `ОбновитьПовторноИспользуемыеЗначения()` не
помогает. Исправление: перезапуск `rphost` либо программная перезапись карточки задания
(`НаименованиеМетода = "..."; Записать()`). Тело методов применяется без перезапуска и
реструктуризации.

Переименование общего модуля противоречит стандарту 706: создать новый модуль, перенести код,
обновить ссылку в регламентном задании. При обычном обновлении конфигурации перезапуск `rphost` и
`rmngr` не нужен и не предлагается - только при подтвержденном симптоме выше.

## После обновления основной конфигурации из хранилища

- **Расхождение `extendedConfigurationObject`.** После обновления основной конфигурации UUID объекта
  меняется, а в заимствованном `.mdo` расширения остается прежний: деплой отказывает "Значение
  контролируемого свойства не совпадает". Синхронизировать UUID с объектом основной конфигурации
  (расхождение в `Configuration.mdo` расширения - ложное, не исправлять).
- После обновления из хранилища сверять каждый объект задачи: заимствования меняют место, правки
  откатываются, остаются файлы без объекта.
- Длины строковых реквизитов приходят из хранилища урезанными (например 20 вместо 36) - сверять
  квалификаторы после захвата. Форма, испорченная в Конфигураторе после импорта, -
  `edt-zip-export-pitfalls.md`, раздел 5.
