# Поведенческий прогон скилов

`tools/run_skill_evals.py` отвечает на вопрос, которого не задают снапшот-тесты:
**меняет ли скил поведение агента.**

Снапшот-тесты в `tests/skills` проверяют СКРИПТЫ навыка: дал вход, получил файлы,
сверил с эталоном. Детерминированно и без агента. Но скил это не только скрипты:
`SKILL.md` учит агента выбирать инструмент, проверять вызов, не выдумывать имя.
Проверить это можно только прогоном агента.

## Как устроен прогон

Каждый кейс идет дважды.

| Фаза | Что видит агент | Что показывает |
|---|---|---|
| RED | скила нет | базовая линия: что модель знает сама |
| GREEN | скил разложен в рабочий каталог агента | что добавил скил |

Скил полезен, когда GREEN проходит, а RED нет. Если проходят обе фазы одинаково,
скил не дал агенту ничего нового, и это результат прогона, а не его отсутствие.

Агент - Codex CLI. Он идет без интерактива, пишет машинный трейс и не тратит
подписку Claude. Прогон изолируется ключами `--ignore-user-config` и
`--sandbox read-only`, иначе установленные глобально скилы и личные правила
протекут в фазу RED и сотрут разницу между фазами.

## Что замеряется

- **Активация** - обращался ли агент к файлам скила. Берется из трейса, а не из
  слов в ответе: агент может назвать скил, не открыв его, и наоборот.
- **expect / forbid** - регулярные выражения по тексту ответа.
- **Вызовы БСП** - блоки BSL из ответа разбираются и сверяются с офлайн-справочником
  `skills/1c-bsp-api/references/bsp-api.jsonl`. Ловятся три класса: выдуманный
  модуль, выдуманный метод, вызов служебного или переопределяемого модуля.
  Выгрузка конфигурации для этого НЕ нужна.

  Имя, которого в справочнике нет, само по себе НЕ претензия: это бывает модуль
  проекта, заглушка примера или платформенный тип. Выдумкой считается только имя,
  ПОХОЖЕЕ на настоящее имя БСП, - так галлюцинация и выглядит. Порог `LOOKALIKE`
  замерен на живом прогоне: выдумки дают 0.80-0.88 (`ФайловаяСистемаКлиентСервер`
  против `ФайловаяСистемаКлиент` - 0.88), чужие имена 0.33-0.57
  (`МойСерверныйМодуль` - 0.49, `ТаблицаЗначений` - 0.52).

  Из разбора исключаются локальные переменные блока и менеджеры объектов
  (`Справочники.`, `Документы.` и прочие): вызов метода на переменной - работа
  с платформенным объектом, а не обращение к общему модулю.
- **Токены** - вход плюс выход по завершенным ходам.

## Запуск

```bash
python tools/run_skill_evals.py --list                      # у каких скилов есть кейсы
python tools/run_skill_evals.py --skill 1c-bsp-api --dry-run   # разобрать кейсы, не запуская агента
python tools/run_skill_evals.py --skill 1c-bsp-api
python tools/run_skill_evals.py --skill 1c-bsp-api --case invented-module-refused
python tools/run_skill_evals.py --skill 1c-bsp-api --phase green
python tools/run_skill_evals.py --skill 1c-bsp-api --jobs 3 --json report.json --artifacts .tmp/answers
```

Коды возврата: 0 пороги достигнуты, 1 не достигнуты, 2 ошибка запуска.

Прогон стоит вызовов к модели и идет минутами, поэтому в CI он не заведен и
запускается руками: перед выпуском и после правки `SKILL.md`.

## Формат кейсов

`skills/<навык>/evals/evals.json`. Старые записи с прозаическими `expectations`
раннер читает, но проверить не может: они остаются описанием для человека.
Машинные проверки задаются полями ниже.

```json
{
  "id": "invented-module-refused",
  "prompt": "задача, которую получает агент",
  "expected_output": "описание для человека, раннером не проверяется",
  "expectations": ["то же, прозой"],
  "expect": ["регулярное выражение, которое ДОЛЖНО найтись"],
  "forbid": ["регулярное выражение, которого быть НЕ должно"],
  "checks_bsl": true
}
```

Кейс без единого машинного поля прогоняется и помечается `no-checks`: видно,
какие скилы еще не переведены на исполняемый формат. Сводку дает `--list`.

## Правила написания кейсов

**Имена модулей и методов сверять по справочнику, а не по памяти.** Кейс,
построенный на выдуманном имени, будет вечно валить верный ответ агента.

```bash
python skills/1c-bsp-api/scripts/bsp-api.py check Пользователи.ТекущийПользователь
```

**Ложное срабатывание дороже пропуска.** Кейс, который валит правильный ответ,
хуже кейса, который пропускает неправильный: по первому чинят исправный скил.
Первый прогон раннера дал три таких случая подряд, все в самом раннере:

1. `forbid` со строкой несуществующего метода сработал на упоминании этого метода
   в тексте `SKILL.md`, который агент вычитал в трейс. Отсюда правило: проверки
   идут ТОЛЬКО по тексту ответа агента. Отката на сырой поток нет намеренно.
2. `ДвоичныеДанные.Размер()` на локальной переменной был объявлен обращением к
   выдуманному модулю БСП. Отсюда фильтр локальных имен и менеджеров.
3. Фаза, где не отработал НИ ОДИН вызов (исчерпан лимит подписки), отчиталась
   как 0 из 5 при нуле ошибок. Отсюда `trace_error` и отдельный код возврата 2:
   сбой прогона нельзя показывать как провал скила.

**Кейс должен различать.** Если RED проходит так же, как GREEN, кейс ничего не
доказывает: модель знала ответ и без скила. Такой кейс либо усложняют, либо
признают, что скил в этой части избыточен.

## Ключи

| Ключ | Что делает |
|---|---|
| `--skill ИМЯ` | какой скил прогонять |
| `--case ID` | только эти кейсы, можно повторять |
| `--phase red\|green\|both` | какие фазы гонять |
| `--jobs N` | параллельных запусков агента |
| `--timeout СЕК` | предел на один запуск |
| `--model ИМЯ` | переопределить модель агента |
| `--codex ПУТЬ` | путь к Codex CLI, по умолчанию ищется пакетный |
| `--artifacts КАТАЛОГ` | сложить ответы агента файлами |
| `--json ФАЙЛ` | записать отчет |
| `--dry-run` | разобрать кейсы и выйти |
| `--list` | скилы с кейсами и сколько из них машинных |

## Происхождение

Замысел двухфазного прогона со сверкой активации по трейсу взят из
[brake71/1c-ssl-skills](https://github.com/brake71/1c-ssl-skills) (MIT,
Чекменев Дмитрий Алексеевич), `ci/run_skill_evals.py`. Реализация своя:
кейсы лежат по скилам вместо общего корпуса, вызовы БСП сверяются с офлайн-справочником
вместо выгрузки конфигурации, Codex резолвится пакетным исполняемым файлом.

## Проверка выбора скила между соседями

Прогон одного скила отвечает на вопрос "помогает ли скил". Маршрутизация отвечает на
другой: "выбирает ли агент ТОТ скил". Раскладывается несколько скилов сразу, смотрится,
чьи файлы агент открыл.

```bash
python tools/run_skill_evals.py --routing tests/routing/config-skills.json --runs 3
```

Набор задает список скилов и запросы трех видов:

| Вид | Что ожидается |
|---|---|
| `direct` | активируется названный скил |
| `adjacent` | активируется любой из названных: запрос стоит на границе тем |
| `off-topic` | не активируется ни один |

Вердикт различает четыре исхода - верный выбор, чужой скил, пропуск, несколько скилов.
Записи "активировался такой-то" мало: ей удовлетворяет и систематически неверный выбор.

Число повторов здесь решает. На одном повторе составной запрос показал пропуск, на трех
устойчиво - открытие нескольких скилов сразу.

## Возобновление прерванного захода

Заход прерывается по исчерпанию квоты исполнителя, и заранее это не предсказать. Ключ
`--resume` записывает сведенный результат каждого кейса в файл, а следующий заход гонит
только недостающее.

```bash
python tools/run_skill_evals.py --skill 1c-bsp-api --resume
```

Сохраненное не пересчитывается: повторный прогон дал бы другой ответ агента и смешал два
замера в один.
